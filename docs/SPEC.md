本書の数値と規則には、根拠の強さを示すラベルを付ける。ラベルによって仕様上の扱いが変わる。

### 0.3 用語

- **ステム**: 楽曲を構成するパート別の音声ファイル。**2mix**: ステレオに混ぜ終えた音声
- **目的関数（objective）**: ミックス／マスタリングの「意図」を、測定可能な代理指標の重み付きで表したもの
- **媒体プロファイル（media profile）**: 出口の制約条件。再生側のラウドネス正規化、True Peak 天井、納品形式など
- **整音（cleanup）**: AI 生成音源特有のノイズやアーティファクトを、ミックスの前に取り除く工程
- **Mix Report**: 全ての測定値と判断を文書化した出力
- **レベルマッチ**: 比較する2つの音声の統合ラウドネスを揃えること

## 1. 製品定義

### 1.1 目的

MankoMIX は、AI 生成楽曲や既存のステムを、**人の耳にとって最高に聞き心地がよいもの**に、あるいは**目的意識（ミックスの目的関数）に沿ったもの**に仕上げるために、AI エージェントの側からミックスとマスタリングを行うツールである。

入力はステム群（または 2mix）、指定するのは「目的関数」と「媒体プロファイル」、出力はその媒体向けのマスター音声と Mix Report である。

### 1.2 製品の芯

1. **実ファイルへの決定的な DSP 処理と実測検証**。生成モデルによる再レンダリングではないので、元の演奏の同一性が保たれ、同じ入力と同じプロジェクトから同じ出力が再現できる
2. **目的関数が一級の設計概念**。デフォルトは「聞き心地の最大化」。重低音強化やボーカル前面などを名前付きで選び、強度を指定し、混合できる
3. **意図と出口の2軸合成**。目的関数（意図）と媒体プロファイル（出口）は独立しており、任意に組み合わせられる（例: 重低音強化 × Spotify、重低音強化 × クラブ）
4. **ステム起点**。ステムの差し替え・追加・再配置（リミックス）をプロジェクト形式で扱う
5. **判断の透明性**。エージェントが決めた全パラメータと理由を Mix Report に残す。提案されたチェーンは後から全て編集できる
6. **整音 → ミックス → マスタリング → ノイズ戻り監視**を1本のパイプラインにする

### 1.3 最終判定は人の耳

自動指標は知覚の代理に過ぎない。本ツールは「測定 → パラメータ決定 → 再測定で検証」のループを回すが、その到達点は「代理指標の上で意図に近づいた」ことであって「良い音になった」ことの証明ではない。この前提を次の形で仕様に固定する。

- Mix Report は必ず「人の耳で確認すべき点」の一覧を含む（§6.8）
- スコアは合計値だけでなく指標別の内訳で提示する
- GUI と README の聴き比べは、レベルマッチした A/B を標準にする（大きい方を良いと錯覚する効果を除くため）
- 重みと閾値は不変条件ではなく、リファレンス実測とオーナーの試聴評価で較正する対象とする（§4.7）

### 1.4 想定ユーザー

- AI エージェント（Claude Code、Codex などの MCP / CLI クライアント）。主軸
- AI 生成楽曲を配信・公開したい制作者
- 自作曲を AI でアレンジし、ステム単位で差し替えながら仕上げたい実務家
- AI 生成に限らず、ステムや 2mix を持つ一般の制作者

### 1.5 非目標

- 楽曲の生成、作曲、歌詞制作
- 生成モデルによる再レンダリング型の「リマスター」（元の演奏が保持されない処理）
- 配信代行、ストアへの申請
- リアルタイムのライブミキシング（プラグイン化は §14 で将来の考慮事項として扱う）
- 入力素材の権利状態の判定（ユーザーの責任。ツールは出所の記録欄だけを持つ）

## 3. アーキテクチャ

### 3.1 層構成

```
┌──────────────────────────────────────────────────────────────┐
│ 顔（faces）   CLI          MCP サーバー         GUI（Web）     │
│               │             │                   │  └ デモ: ブラウザ内モック │
├───────────────┴─────────────┴───────────────────┴────────────┤
│ コア API（ヘッドレス）                                         │
│  プロジェクト管理 / 入力アダプタ / 解析・測定 / 目的関数評価    │
│  プランナー（決定的） / 検証 / Mix Report / モデルレジストリ    │
├──────────────────────────────────────────────────────────────┤
│ DSP エンジン（プロセッサグラフの実行）                         │
│  バックエンド: FFmpeg（外部プロセス） / ネイティブ核 / 参照実装 │
├──────────────────────────────────────────────────────────────┤
│ 正本: project.json ＋ 素材（相対パス＋内容ハッシュ）           │
└──────────────────────────────────────────────────────────────┘
```

- **コア API**: 全機能の唯一の入口。CLI・MCP・GUI バックエンドはここを薄く包むだけにする
- **プランナー**: 測定値、目的関数、媒体プロファイル、判断規則（§7.3）から処理計画を作る決定的ロジック。LLM を使わない。外部エージェントは、プランナーの提案をそのまま適用することも、書き換えることも、自分で計画を書くこともできる
- **DSP エンジン**: 抽象プロセッサ（§6.5.2）のグラフを受け取り、バックエンドに割り当てて実行する。グラフ記述は JSON で、これがプラグイン化の際の共有契約になる（§14）

### 3.2 DSP バックエンド

| バックエンド | 中身 | ライセンス上の位置 | 用途 |
|---|---|---|---|
| `ffmpeg` | ユーザー環境の FFmpeg を外部プロセスとして呼ぶ | LGPL 構成に含まれる機能だけを使う。コードを取り込まず、バイナリを配らない（§13.3） | デコード／エンコード、リサンプル、基本的な EQ・ダイナミクス、ラウドネス計測、コーデック往復 |
| `native` | 自前のネイティブ DSP 核。Airwindows（MIT）由来のプロセッサと自作プロセッサをパラメータ駆動のオフラインレンダラとして束ねる | MIT / Apache-2.0 のみ | 音作り（サチュレーション、クリッパー、コンプ、リミッター等）。将来のプラグイン核 |
| `reference` | 数値計算ライブラリ上の参照実装 | BSD / MIT / ISC 系のみ | スペクトル処理（整音）、測定、ネイティブ核へ移植する前の検証用実装 |

一つの抽象プロセッサが複数のバックエンド実装を持ってよい。どのバックエンドで実行したかはレンダリング記録（§9.6）に残す。

### 3.3 実装スタック（確定。D-034、D-042）

| 層 | 採用 | 理由 |
|---|---|---|
| コア、CLI、MCP サーバー | **Python**（3.11 以上） | 解析（librosa）、測定（pyloudnorm）、分離統合層（python-audio-separator）が全て Python で揃う |
| ネイティブ DSP 核 | **C++17**（C ABI を公開。ビルドは CMake） | Airwindows が C++ であり、将来プラグインシェルから同じ核を呼べる |
| GUI | **TypeScript ＋ React ＋ Vite** の Web SPA | 静的ファイルとして出力でき、GitHub Pages のデモにそのまま載る。バックエンド接続をインターフェースで抽象化し、ローカルサーバー接続とブラウザ内モックを差し替える（§11） |
| GUI 用ローカルサーバー | Python（コアと同じプロセス。HTTP ＋ 変更通知） | コア API を直接呼べる |

- ネイティブ核が要らない範囲（M1〜M3）は、Python と FFmpeg だけで動くようにする。ネイティブ核は M4 で導入する
- GUI のフレームワークは、実装フェーズで先行プロジェクトとの共通化に明確な利点が見つかった場合に限り、決定記録を残して差し替えてよい。バックエンド接続のインターフェースと「ローカル接続／デモ用モック」の二実装という構造は変えない

**対応プラットフォーム**

- 最初の対応 OS は **Windows 10 / 11（x64）**。開発と検証の基準環境とする
- コア、CLI、MCP は最初から OS に依存しない書き方をする（パスの扱い、外部プロセスの起動）。**Linux と macOS は公開（M9）までに、コアと CLI の動作を確認する**。GUI はブラウザで動くので OS を問わない
- GPU が要るのはステム分離だけである。基準は NVIDIA の VRAM 10 GB 級。GPU がない環境のために、CPU で動く軽量モデル（SCNet 系）を公式カタログに必ず持つ。分離以外の全工程は CPU で動く

## 4. 目的関数モデル

### 4.1 一般形

```
候補 x（＝プロジェクトの処理パラメータ一式）に対して

  1. 安全不変条件 S-nn を1つでも満たさない候補は、score 以前に棄却する
  2. score(x) = Σ wᵢ × penaltyᵢ(x)        （小さいほど良い。0 が理想）
  3. トランスレーション・ゲート（OF-5）に落第した候補は、score に関わらず是正対象とする
```

- `penaltyᵢ` は代理指標 P-nn の、目標からの偏差を正規化した値。「目標範囲内なら 0、外れるほど 0 → 1 に増える」形に揃える [モデル]
- 目標範囲は原則として**リファレンス集合の実測分布（中央値と四分位範囲）**から取る。固定絶対値はジャンル差に弱いため、リファレンスがない場合の代替としてのみ使う（§4.6）
- 重み `wᵢ` の初期値の決め方: (a) 知覚感度が高い次元ほど重くする（等ラウドネス曲線で 2〜5 kHz が最大感度）、(b) 失敗コストが高いものは重みでなく制約にする、(c) ジャンル慣行は初期値にだけ影響させる
- **全ての penalty 計算はレベルマッチ後の信号で行う**（R-01）
- 比較のための音量揃え（レベルマッチ）は比較専用である。揃えた信号を納品の合否に使わず、納品の検査（S-01、S-02 など）は出口ごとの最終出力で行う（§6.7）
- 周波数軸の評価は線形 Hz でなく **ERB / Bark の知覚帯域**で行う。ステムはソロでなくフルミックス文脈で評価する（R-02）

### 4.2 代理指標の台帳（測定ベクトル）

目的関数は全て、この共通の測定ベクトルから合成する。新しい目的関数の追加は「新しい重み付け」であって「新しい測定器」ではない、を原則とする。

| ID | 代理指標 | 定義の骨子 | 確立度 |
|---|---|---|---|
| P-01 | LTAS 帯域偏差 | 長期平均スペクトルを ERB 帯域で集計し、等ラウドネス（ISO 226）の知覚重みをかけて、リファレンス分布からの偏差を測る | [モデル] |
| P-02 | マスキング・リスク | ステム間スペクトルに上方拡散を含む拡散関数を適用し、帯域ごとの「埋もれ量 dB」を推定する。対象別（対主役／全体／低域発→中域）に集計する | [モデル] |
| P-03 | ラウドネス・ダイナミクス群 | Integrated LUFS、Short-term 分布、LRA、PLR（TP − Integrated）、PSR（TP − Short-term 最大） | [規格] 測定法 |
| P-04 | 帯域別クレスト | 帯域ごとの Peak − RMS。測定区間を必ず併記する | [規格] |
| P-05 | 帯域別相関・Side 比 | 帯域別の L/R 相関と S/(M+S) エネルギー比のベクトル | [規格] 測定法 |
| P-06 | モノ損失 | モノ合算前後の帯域別レベル差 dB。要素別の消失検出を含む | [規格] |
| P-07 | 帯域エネルギー比 | サブ（20〜60 Hz）、バス（60〜250 Hz）、低中域（200〜800 Hz）などの全帯域に対する比 | [規格] 測定法 |
| P-08 | 倍音補完インデックス | 基本音帯域のエネルギーに対する第2・第3倍音帯域のエネルギー比 | [モデル] |
| P-09 | 奥行き順序 | ステム別の depth スコア（レベル、D/R、高域比、プリディレイの合成）と、宣言された前後関係との順序整合 | [モデル] |
| P-10 | 主役帯域レベル差 | 主役（通常はボーカル）の明瞭度帯域（300 Hz〜5 kHz）と伴奏の同帯域のレベル差 | [モデル] |
| P-11 | ハーシュネス | 2〜5 kHz の短期エネルギー突出（LTAS 比とピーク性） | [モデル]（疲労との対応は弱証拠） |
| P-12 | トランジェント保持 | 処理前後の帯域別クレスト変化、アタック区間のエネルギー比 | [モデル] |
| P-13 | 低域チューニング整合 | キックとベースの基本周波数差（セント）、キーのトニック周波数のサブ帯域判定 | [規格] 換算式 |
| P-14 | 配信安全 | True Peak（4 倍以上のオーバーサンプリング測定）、想定コーデック通過後の TP | [規格] |
| P-15 | 残響指標 | 対象要素の D/R 比、帯域別 RT60 の実測 | [モデル] |
| P-16 | ノイズ・シマー指標 | 静音区間のノイズ床、高域（既定 10〜14 kHz）のシマー指標（帯域別スペクトル平坦度と信号相関変調）、高域の頭打ち周波数 | [モデル]（§6.4） |
| P-17 | シビランス | 5〜8 kHz の歯擦音区間の突出 | [モデル] |
| P-18 | リミッター依存度 | リミッターのゲインリダクションの統計（中央値、95 パーセンタイル、持続率） | [慣行] 閾値 |
| P-19 | スペクトル滑らかさ | LTAS の狭帯域の凹凸（共振、コムフィルタ、過度なノッチ／ブースト）の量 | [モデル] |
| P-20 | セクション間コントラスト | セクション別（静かな部分と盛り上がる部分）の Short-term ラウドネス差と帯域の開き方。処理前後で保存されているかを見る | [モデル] |
| P-21 | 整音の副作用 | 整音前後のステレオ幅変化（P-05 の差）と低中域 250〜500 Hz のエネルギー変化 | [規格] 測定法 |
| P-22 | 帯域あたりの主役数（密度） | 6 帯域（サブ 20〜60 Hz、バス 60〜250 Hz、ローミッド 250〜500 Hz、ミッド 500 Hz〜2 kHz、ハイミッド 2〜6 kHz、エア 6〜20 kHz）ごとに、その帯域のエネルギーを主に担っているステムの数を、セクション別に数える。目安は帯域あたり 1〜2 | [慣行] 目安 |

補足:

- P-02 は、ステム重要度（§4.11）で重み付けした埋もれ量として集計する。重要度の高いステムが埋もれることを重く、低いステムが埋もれることを軽く罰する
- P-22 は P-02 と別の指標である。P-02 が「どれだけ埋もれているか」を測るのに対し、P-22 は「同じ帯域に主役が何人いるか」を数える。「重ねると濁る」の主因は楽器の数でなく同じ帯域への集中なので、密度の高い編成では EQ より先に帯域の主役交代を提案する材料になる（R-28）
- P-01 の目標は**平坦でも Harman カーブでもない**。Harman カーブは再生系（ヘッドホン）の目標であり、ミックス自体のスペクトル目標に流用することを仕様で禁止する（R-17）
- P-03 の LUFS は配信適合の物差しであって、快さの物差しではない。K 特性は低域を小さく測るため、低域目的（OF-1 など）は LUFS で評価せず P-07 で評価する
- P-01 の等ラウドネス（ISO 226）の知覚重みは、純音を使った聴取実験に基づく近似である。音楽の帯域の重みとして使うのは実験の範囲の外への転用である（定義は上の表のとおり）
- P-19 は「スペクトルの滑らかさが選好の最大の説明因子である」という再生系の選好研究を、ミックス側の診断に転用したもの。転用である旨を Mix Report に書く
- P-20 は「快さは予期と到達の2相で生じる」という知見の反映。均一化しすぎる処理が展開を平坦にしないことを監視する
- より精密な知覚ラウドネス（ISO 532 系）と音質指標（シャープネス、ラフネス、変動強度）は、将来の測定器拡張の候補とする。その場合も目的関数の一般形は変えない（§17 の拡張項目）

### 4.4 目的関数カタログ

重みは初期案（合計 1.0）であり、較正前提である。固定仕様ではない。

| ID | 名前（`id`） | 一言で | 主要な代理指標（初期重み） | 特に効く制約 |
|---|---|---|---|---|
| OF-0 | 聞き心地（`comfort`）**デフォルト** | 偏りがなく、疲れにくく、要素が聞き分けられる | P-01 (0.25)、P-02 (0.20)、P-11 (0.15)、P-03 (0.15)、P-09 (0.10)、P-12 (0.10)、P-19 (0.05) | S-01〜S-04 |

| OF-2 | ボーカル前面（`vocal_forward`） | 声を最も近く、埋もれさせない | P-10 (0.30)、P-02 対ボーカル (0.30)、P-09 (0.15)、P-15 (0.15)、P-17 (0.10) | S-04（ボーカルのモノ損失ほぼ 0） |

| OF-4 | クラブ・インパクト（`club_impact`） | 大音量・モノ PA・サブウーファー前提での衝撃とグルーヴ | P-07 再生可能帯域 (0.25)、P-03 の PSR (0.20)、P-02 時間軸版 (0.20)、P-04 キック帯域 (0.20)、P-13 (0.15) | S-03、S-04 を最も厳しく |
| OF-5 | トランスレーション堅牢性（`translation`）**ゲート型** | どの再生環境でも意図が保存される | score でなく合否（§4.5） | ゲート自体が制約 |
| OF-6 | 疲れにくさ（`low_fatigue`）**暫定** | ループ再生や長時間再生で疲れにくい | P-11 (0.30)、P-03 の LRA・密度 (0.25)、P-17 (0.15)、P-16 (0.15)、P-19 (0.15) | S-01〜S-04 |

各目的関数の設計意図:

- **OF-0 聞き心地**: 選好研究で最も証拠が強いのはトーンバランスなので P-01 を最大重みにする。目標はジャンル別リファレンス分布である。P-02 は「要素が聞き分けられる」ことの直接の代理。P-11 は耳の最感度帯域の過剰を罰する。低域を盛れば P-01 と P-02 が悪化し、高域を盛れば P-11 が悪化するので、「盛れば解決」が成立しない構成になっている
- **OF-1 重低音強化**: 主役は P-07。ただし低域強化は上方拡散により必ず 200〜800 Hz の明瞭さを犠牲にするので、P-02 の低域発マスキングを差し引く。これを入れないと際限なく盛る。P-08 は「大きくした低音が小型スピーカーで消える」失敗への保険で、サブ増強と倍音付加をセットで設計する。サブを上げると再生側の正規化で全体が下げられ、中域が相対的に下がるトレードオフを Mix Report に必ず書く
- **OF-2 ボーカル前面**: 「前面」は単一量でなく、レベル差（P-10）、埋もれ（P-02）、奥行き順序（P-09）の複合として定義する。P-02 は低中域 200〜800 Hz の競合と明瞭度帯域 2〜5 kHz の競合を別々に罰する。シビランスは前面化の副作用として罰する
- **OF-3 明瞭さ**: 「主役帯域の SN 比」と「時間軸の輪郭」の積として扱う。プレゼンスは不足でも過剰でも罰する両側ペナルティ。OF-2 が特定要素（ボーカル）の前面化であるのに対し、OF-3 は主役一般の聞き取りやすさ。歌詞の明瞭さを求める用途はここに当たる
- **OF-4 クラブ・インパクト**: 正規化がなく、モノ PA とサブウーファーが前提という、配信とは逆の世界。ラウドネス目標と天井は媒体プロファイル（`club`）が持ち、目的関数は「衝撃の質」を担う。P-02 の時間軸版は、サイドチェインによるキック帯域のアンマスキング量と、その回復が音価に合っているかを見る
- **OF-6 疲れにくさ**: BRIEF が例示する「ループ再生での疲れにくさ」に対応する。聴覚疲労を定量した査読研究は弱いため、**暫定の目的関数**とし、Mix Report に弱証拠である旨を表示する

### 4.5 トランスレーション・ゲート（OF-5）

他の目的関数の後段に常に置く合否判定。落第した場合は score の良し悪しに関わらず是正提案を出す。

1. **帯域制限プレビュー**（小口径スピーカー想定の帯域制限）で主役が保存されている
2. **モノ合算**の帯域別損失（P-06）が閾値内
3. **小音量相当**（等ラウドネス補正後）でも主役と伴奏の関係が保存されている
4. **基本音を落とした条件**で、倍音補完インデックス（P-08）が低音の音高の保存を示す

「トランスレーション」とは全環境で同じ音になることではなく、重要な要素（ボーカル、キックとベースの関係、リズム）の知覚が保存されることである。媒体プロファイルは、どのチェックをどの厳しさで適用するかを `playback_assumptions` で指定する（§5.2）。

### 4.6 目標の出どころ（リファレンス集合）

P-01 をはじめ多くの penalty は「リファレンス分布からの偏差」で定義される。分布の出どころを次の優先順で決める。

1. **ユーザーが登録したリファレンス曲**（1〜3 曲を推奨）。取り込み時に測定ベクトルだけを抽出して保存する。音声そのものはプロジェクトに含めない
2. **リファレンス集合**（ジャンル別などの複数曲の統計。中央値と四分位範囲）。ユーザーが自分の手元の曲から作る。**v1 では、市販曲から得た統計をリポジトリに同梱しない**（D-039）。音声を含まない統計値であっても、選曲の責任と権利上の確認が要るため、同梱の可否は較正のマイルストーン（M10）で、公開監査を通したうえで改めて判断する
3. **汎用 prior**。上の2つがない場合の代替。許容幅を広く取り、Mix Report に「汎用の目安に対する評価であり、ジャンルに合わせた評価ではない」と明記する

リファレンスの使い方の規則:

- リファレンス側を下げてレベルマッチする（R-01）
- スペクトルをそのまま写す EQ マッチはしない。編成が違えば最適なスペクトルも違うので、リファレンスは「分布の物差し」として使う
- 一度に比べる問いは1つにする（低域の量、主役のレベル、幅、ダイナミクス、帯域別バランス）

**物差しと原液の境界（2026-11-15 追記）**: 本節のリファレンス（コアが目標分布に使う「物差し」）とは別に、指揮レイヤーには利用者が持ち込んだマスター／ステムを測って指揮者が読む資料にする「原液」の経路がある（`docs/DIRECTION_FORMAT.md` §6）。両者は次のとおり分かれ、原液の経路はコア・床・ゲートに触れない。

| | 物差し（本節。既存・不変） | 原液（指揮レイヤー） |
|---|---|---|
| 入口 | `mankomix reference add/list/remove` | `mankomix direction ref …` |
| 置き場 | プロジェクト内 `analysis/ref_<id>.json` | kb の `references/`（第三者作品は既定で非公開の `_private/kb/`） |
| 読み手 | コア（目的関数の目標分布） | 指揮者だけ。コアは読まない |
| 床への影響 | あり（登録すると目標分布が変わる） | なし。原液の経路はプロジェクトの `references` に書かない |
| 単位 | プロジェクトごとの曲 | 作品・技術者（案件をまたいで再利用） |

- 原液の取り込みが物差しを自動登録することはない。両方使いたい場合は両方のコマンドを打つ。これにより、原液を取り込んでも床はビット同一に保たれる
- 上の使い方の規則のうち「EQ マッチで写さない」「一度に比べる問いは1つ」は原液の経路にもそのまま適用する。原液の経路にも目標カーブへの自動一致は無い
- D-039（市販曲の統計を同梱しない）は原液の経路でも変わらない。公開リポジトリの kb に置ける作品は自前の作品（`rights: own`）だけ
- **汎用ガイドとの対照（2026-11-15 追記 2）**: 指揮レイヤーの `direction ref compare --add guide` は、汎用 prior（`knowledge/thresholds_m3.json` の `p01_generic_prior`）からの形の偏差を参照とこちらの両方について並べる、指揮者の読みの材料である。目標・寄せる処理・較正の入力ではなく、どの判定にも入らない。使わなくても不利にならず、validate／check は使用の有無を見ない
- ジャンル固有の目標カーブを同梱しない方針（R-17）と D-039 は変わらない。ジャンルに当たる目標の出どころは、従来どおり利用者が登録した物差し（上の 1・2）だけである

### 4.7 目的関数の指定・混合・強度

プロジェクトでの指定は次の形を取る。

```json
{
  "objective": {
    "blend": [
      { "id": "comfort", "weight": 0.6 },
      { "id": "bass_heavy", "weight": 0.4 }
    ],
    "intensity": 0.7,
    "overrides": { "bass_heavy": { "sub_band_hz": [30, 60] } },
    "lead_stem": "vocals"
  }
}
```

- **blend**: 目的関数は排他ではない。「聞き心地を土台に重低音を足す」は重みの混合で表す。制約（S-nn）は混合しても緩和されない
- **intensity**（0〜1）: 目標範囲を、リファレンスの中央値から目的関数の方向へどれだけ寄せるかの強度。0 は OF-0 と同じ、1 は目的関数が定める上限まで。意図の語彙と強度を分ける設計にする（DSP パラメータを直接指定させない）
- **lead_stem**: 主役の宣言。OF-2、OF-3、P-09、P-10 は主役の宣言に依存する。未指定ならボーカル系ステムを主役と推定し、推定である旨を記録する
- **overrides**: 目的関数ごとの公開パラメータ。公開するパラメータは定義ファイルが宣言する

### 4.8 目的関数の定義ファイル

目的関数は `objectives/` 配下の JSON で定義する。スキーマは `schemas/objective.schema.json`（実装フェーズで確定）。骨子:

```json
{
  "id": "bass_heavy",
  "schema_version": 1,
  "label": { "ja": "重低音強化", "en": "Bass heavy" },
  "kind": "score",
  "status": "draft",
  "summary": { "ja": "低域の量と質を最大化しつつ濁らせない" },
  "terms": [
    { "metric": "P-07", "variant": "sub+bass", "weight": 0.35, "sense": "raise_to_target" },
    { "metric": "P-13", "weight": 0.20, "sense": "minimize" },
    { "metric": "P-02", "variant": "low_to_mid", "weight": 0.20, "sense": "minimize" },
    { "metric": "P-08", "weight": 0.15, "sense": "raise_to_target" },
    { "metric": "P-03", "variant": "plr", "weight": 0.10, "sense": "keep_in_range" }
  ],
  "constraints_emphasis": ["S-03", "S-04"],
  "params": { "sub_band_hz": { "default": [20, 60] } },
  "report_notes": ["normalization_tradeoff"],
  "evidence": "weights are initial values subject to calibration"
}
```

ユーザー定義の目的関数も同じ形式で追加できる。検証コマンド（§10）が、未知の指標 ID、重みの合計、制約の緩和（禁止）を検査する。

### 4.9 較正

- 重みと閾値は学習対象である。較正の入力は (a) リファレンス集合の実測分布、(b) オーナーと協力者のレベルマッチ済みブラインド A/B 評価（§16.5）
- 較正結果は `objectives/` と `knowledge/` のデータの版として記録する。Mix Report は使用した定義の版を必ず記録する
- 較正で制約（S-nn）を目的関数側へ降格することはしない

### 4.10 ジャンル prior

ジャンルの慣行は、目的関数の**重みと目標範囲の初期値**にだけ影響させる（§4.1 の原則 c）。ジャンル prior は目的関数でも制約でもなく、「このジャンルならまずここから始める」という出発点である。リファレンスの実測があればそちらが優先し、ユーザーの指定は常に prior を上書きする。

- ジャンルはプロジェクトの `genre` で宣言する。未指定なら prior を使わず、汎用の初期値で進める。**ジャンルはユーザーかエージェントが宣言する。v1 では音からの自動推定をしない**（D-053）。寛容ライセンスで使えるジャンル推定の手段が手元になく、誤った推定で prior が黙って切り替わる方が、未指定で汎用の初期値を使うより害が大きいため。未指定のときは、Mix Report に「ジャンル未指定のため汎用の初期値で評価した」と書く
- prior の正本は `knowledge/genre_priors.json`。全て [慣行] であり、較正の対象である
- prior が決めるのは次の4点: (1) 低域の主導役（キック主導かベース主導か）、(2) 主役帯域レベル差 P-10 の目標帯、(3) 重くする代理指標、(4) ステム重要度の既定順（§4.11）
- 媒体プロファイルとは別の表で持つ。媒体は出口の条件、ジャンルは意図の出発点であり、混ぜない

| ジャンル（`id`） | 低域の主導 | P-10 目標帯（暫定） | 重くする指標と初期設定 | 根拠の強さ |
|---|---|---|---|---|
| J-POP（`jpop`） | 曲ごとに決める | 高め（+2〜+6 dB） | 対ボーカルの P-02 を最優先。密度が高いので P-02 の閾値を厳しめに | 実務慣行 |
| アニソン（`anison`） | 曲ごとに決める | 高め | 対ボーカルの P-02、P-11 を両側で（高域を盛ると刺さりやすい）。P-22 を厳しめに。残響は短め | 実務慣行（ジャンル固有の一次資料は未確認） |
| アイドル／ダンスポップ（`idol_pop`） | キック主導 | 高め | グループボーカルは「主役と脇役」の重要度階層で扱い、ハモりは主役帯域を譲る。明るさは P-01 で評価し、過剰は P-11 で罰する | 実務慣行（同上） |
| ヒップホップ（`hiphop`） | キック主導 | 高め（+2〜+5 dB） | P-13、P-02 の時間軸版（サイドチェインによるアンマスキング）。808 の P-08 を必須の評価項目に。残響は短め、ドライ寄り | 実務慣行 |
| EDM（`edm`） | キックがパルス、サブはモノ | 中低（0〜+3 dB） | 低域モノ（S-03、S-04）を最も厳しく。ダッキング量と回復の音価整合。P-08（小型スピーカーでのベースラインの認識） | 実務慣行 |
| ロック（`rock`） | ベース主導 | 中（0〜+3 dB） | P-13 と P-07 をベース寄りに評価。ドラムバスの軽いまとめを既定チェーンに。LRA と PLR は広めを許容し、潰しすぎを罰する | 実務慣行 |
| R&B／バラード（`rnb_ballad`） | ベースの歌い回しを生かす | 中高（+1〜+4 dB） | P-09、P-15（声は近く、残響は長くても D/R を高く）。LRA は広めを許容。P-20 を評価に入れる | 実務慣行 |
| クラブ向け（`club_track`） | キックとサブ | 低め（声は要素の一つ） | `club_impact` と媒体 `club` の合成の典型。モノ合算の検査（P-06）を合否ゲートに格上げ。イントロとアウトロの構成を保つ | 実務慣行 |

- P-10 目標帯の dB 値は「初期の目安」で、リファレンス集合の実測で置き換える前提である。**数値そのものより、ジャンル間の順序（どのジャンルが相対的に声を前に出すか）の方が頑健**なので、実測がない段階では順序を守ることを優先する
- 目標帯を外れた場合は、Mix Report に「声が埋もれている」「声が浮いている」と書く
- 「低域の主導」は、どちらが最低オクターブを持つかの役割割り当て（R-08）の初期値になる
- ジャンルの語彙は `knowledge/` のデータなので、ユーザーが独自のジャンル prior を追加できる

### 4.11 ステム重要度

マスキングは「誰が誰に譲るか」を決めないと解けない。その順位を、ステム重要度としてプロジェクトに持つ。

- 既定の順: **主役（リードボーカル）＞ リズムの核（キック、スネア）＞ 低域の土台（ベース、808）＞ ハーモニー・コード楽器 ＞ パッド、FX、装飾**
- ジャンル prior がこの順を入れ替える（ヒップホップではキックと 808 が最上位に並ぶ。ロックではベースの順位が上がる）
- 重要度は固定値でない。**セクションごとに変わる**（サビでは主役の重みを上げる、など）。プロジェクトでは、トラックの既定値と、セクション別の上書きで表す
- ユーザーとエージェントは重要度を上書きできる。prior から来た値か、明示された値かを記録する

重要度の使い道:

1. P-02 の集計の重み（重要度の高いステムの埋もれを重く罰する）
2. 是正の方向。マスキングが EQ で解けないとき、**重要度の高い側を極端に加工するより、低い側を下げる・区間をミュートする**ことを優先する（R-28）
3. 帯域の主役の割り当て。帯域ごとの主役は 1〜2 個まで（P-22）とし、主役の座は重要度の高いステムに渡す
4. Mix Report の説明（「サビではボーカルを主役とし、シンセが 1〜3 kHz を譲った」）

## 5. 媒体プロファイル

### 5.1 位置づけ

媒体プロファイルは「出口の制約条件」である。ラウドネスの数値は**納品規格ではなく再生時の正規化レベル**であり、音作りの目標そのものではない。したがって本ツールは、ラウドネス値を「到達すべきトロフィー」ではなく「配送条件（ゲート）」として扱う（R-18）。「音圧競争に勝つ」項は、どの目的関数にも置かない。

- 正規化される媒体では、目標値に合わせ、ダイナミクスを守る
- 正規化されない媒体（クラブ、CD、SNS の熱い版）では、プロファイルが定める実務レンジの中で、目的関数とリミッター依存度（P-18）の制約下で到達できる値を取る
- 目標に届かない場合、リミッターを深く掛けて届かせるのではなく、ミックス段へ差し戻す（R-14、R-15）

### 5.2 プロファイル定義

数値の正本は `profiles/media_profiles.json`。値は時点情報（2026-11 の調査時点）であり、プラットフォーム側の改定がありうるので、各プロファイルは確認日と公式度を持つ。公式に数値を公表しているのは Spotify のみで、他は実測と業界の一致に基づく。

| `id` | 媒体 | LUFS-I 目標（許容レンジ） | TP 天井 | 正規化の挙動 | 公式度 |
|---|---|---|---|---|---|
| `streaming_universal` | ストリーミング共通の安全既定 | −14 | −1.0 | — | 業界の一致 |
| `spotify` | Spotify | −14 | −1.0。マスターが −14 より大きい場合は −2.0 | 両方向 | **公式** |
| `youtube` | YouTube（MV を含む） | −14 | −1.0 | 下げるのみ | 実測の一致 |
| `apple_music` | Apple Music | −16 | −1.0 | 両方向 | 業界の一致（AES 推奨と整合） |
| `amazon_music` | Amazon Music | −14 | −2.0 | 下げるのみ | 報告値 |
| `tidal` | Tidal | −14 | −1.0 | 下げるのみ。アルバム単位 | 実測の一致 |
| `sns_safe` | TikTok / Instagram の安全既定 | −14 | −1.0 | 文脈依存 | 公式値なし |
| `sns_hot` | SNS 専用の熱いバリアント | −9（−11〜−7） | −1.0 | 実質非正規化の場面がある | 実務目安。意図的な選択として使う |
| `club` | クラブ／DJ | −7（−9〜−6） | −0.5（−0.8〜−0.3） | なし | 実務慣行 |
| `cd` | CD（Red Book） | −10（−12〜−9） | −0.3 | なし | 実務慣行 |
| `soundcloud` | 非正規化プラットフォーム | 指定なし（目的関数と P-18 の制約で決まる） | −1.0 | なし | 実務慣行 |

- MV は YouTube と同一仕様であり、別プロファイルを作らない（`mv` は `youtube` の別名）
- レンジを持つプロファイルの既定値（表の左側の値）は確定とする（D-046）: `sns_hot` −9 LUFS、`club` −7 LUFS と天井 −0.5 dBTP、`cd` −10 LUFS と天井 −0.3 dBTP。いずれも調査のレンジの中ほどで、リミッター依存度（P-18）の制約に掛かりにくい側に置いた。レンジ内であれば、ユーザーは出口ごとに目標を指定できる
- **v1 は 1 プロジェクト 1 曲**とし、アルバムモード（複数曲のラウドネスとトーンの統一）は持たない（D-047）。`tidal` は、1 曲をアルバムとみなして扱う。アルバムモードは v1 の後の拡張（M10）とする

プロファイルの構造:

```json
{
  "id": "spotify",
  "label": { "ja": "Spotify", "en": "Spotify" },
  "kind": "streaming",
  "loudness": {
    "target_lufs_i": -14.0,
    "window_lufs_i": [-15.0, -13.5],
    "normalization": "both",
    "policy": "gate"
  },
  "true_peak": {
    "ceiling_dbtp": -1.0,
    "conditional": [{ "when": "lufs_i > -14.0", "ceiling_dbtp": -2.0 }]
  },
  "codec_checks": ["ogg_vorbis", "aac"],
  "playback_assumptions": {
    "mono_low_band_hz": 120,
    "small_speaker_check": true,
    "mono_fold_check": true,
    "low_level_check": true
  },
  "default_delivery": "hires_native",
  "source": { "confidence": "official", "as_of": "2026-11-13" }
}
```

`window_lufs_i` などの許容幅は初期値である。

### 5.3 納品形式（delivery）

媒体プロファイル（再生側の条件）と納品形式（ファイルの条件）は分けて持ち、組み合わせる。ディストリビューターの納品要件はラウドネスを課さないので、プロファイルでなく納品形式として表す。

| `id` | 形式 | 用途 |
|---|---|---|
| `archive_f32` | ネイティブのサンプルレート、32 bit 浮動小数点 WAV | 保管用マスター。ディザなし |
| `hires_native` | ネイティブのサンプルレート、24 bit WAV / FLAC | 高解像度での納品 |
| `distributor_44k16` | 44.1 kHz、16 bit、ステレオ WAV（TPDF ディザ） | ディストリビューター納品の基準線（TuneCore が受け付ける形式。TuneCore の推奨は 24 bit / 192 kHz の WAV。D-064） |
| `cd_redbook` | 44.1 kHz、16 bit、ステレオ（TPDF ディザ） | CD マスター |
| `dj_wav` | 44.1 / 48 kHz、24 bit WAV または AIFF | DJ 用 |

- マスターの保管形式（最高解像度）と、配信基準線への変換を分離する
- 16 bit / 24 bit の WAV は `WAVE_FORMAT_PCM` で書き出す（拡張形式を受け付けない納品先があるため）
- サンプルレート変換と深度削減は書き出しモジュールだけが行う。深度が減るときだけ、最後に1回ディザを掛ける（S-05）。ノイズシェーピングは既定で使わない（後段にロッシー符号化がある場合の相性を考慮）
- ロッシー形式（MP3 など）はマスターとして書き出さない。試聴用のプレビュー書き出しは別扱いにする

### 5.4 2軸の合成

目的関数と媒体プロファイルは独立した軸である。合成の規則:

| 項目 | 決める側 |
|---|---|
| 何を良くするか（重み、目標方向、強度） | 目的関数 |
| ラウドネスの目標とレンジ、TP 天井、コーデック検査 | 媒体プロファイル |
| ファイル形式、サンプルレート、ビット深度、ディザ | 納品形式 |
| 壊れてはならない条件 | 安全不変条件（どちらの軸でも緩和不可） |
| トランスレーション検査の厳しさ | 媒体プロファイルの `playback_assumptions` |

一つのプロジェクトは、同じミックスから複数の「出口」（プロファイル × 納品形式の組）を書き出せる。典型は「ストリーミング用 −14」と「クラブ用」の2マスター運用である。目的関数まで変える場合（例: 配信版は `comfort`、クラブ版は `club_impact`）は、プロジェクト内の**バリアント**として持つ（§9.4）。

## 6. パイプライン

```
入力アダプタ → [任意] ステム分離 → 解析 → 整音 → ミックス → マスタリング → 検証 ＋ Mix Report
```

各段は「入力測定 → 計画 → 実行 → 出力測定 → 段ゲート判定」の形を取る。段ゲートに落ちたら次段へ進まず、是正するか、理由を付けて差し戻す。

### 6.1 入力アダプタ

- 入力層に「ソースアダプタ」の差し込み口を設ける。v1 で実装するのは**ファイル入力アダプタのみ**
- 外部サービス連携（Suno の MCP など）は将来のアダプタとして追加できるようにし、コアは依存しない

アダプタの契約（概念）:

```
SourceAdapter
  id            アダプタ識別子（例: "file"）
  probe(src)    入力を調べ、扱えるかと内容の概要を返す
  fetch(src, dest) 素材をプロジェクトの素材置き場へ取り込み、取り込み記録を返す
```

取り込み記録には、ファイルごとの内容ハッシュ、形式、尺、推定した役割（ファイル名からの推定）、ユーザーが申告した出所（任意）を含める。

#### 6.1.1 ファイル入力アダプタ

- 入力: ステム群のフォルダ、単一の 2mix、または両方（ステム＋参照用フルミックス）
- 形式: WAV / AIFF / FLAC を正式対応とする。ロッシー形式は受け付けるが警告を出す（分離と整音の品質が落ちるため）
- 役割の語彙（初期）: `vocals`, `backing_vocals`, `drums`, `percussion`, `bass`, `guitar`, `keyboard`, `synth`, `strings`, `brass`, `woodwinds`, `fx`, `other`, `fullmix`

#### 6.1.2 無加工取り込みの原則（A-12）

**ダウンロードしたままのファイル群が、そのまま入力になる。** ユーザーにもエージェントにも、取り込み前の前処理を要求しない。

| してはならないこと（取り込みの前提にしない） | 代わりにすること |
|---|---|
| 形式の変換、再エンコード | 元の形式のまま読む |
| リサンプル | サンプルレートを記録する。変換はレンダリング時にだけ行う |
| ラウドネスやピークの正規化 | レベルを測って記録する |
| ファイルの並び替え、リネーム | 元のファイル名を取り込み記録に残し、役割は名前から推定する |
| 尺をそろえるための切り詰めや詰め物 | 尺を測って記録する。そろえるのはレンダリング時（§6.1.5） |

- 取り込みは、素材をバイト単位で同一のまま素材置き場へ複製する（または外部に置いたまま参照する）。複製の前後で内容ハッシュが一致することを確認する
- 取り込み検査で見つけた差異は、**警告か差し戻し**として報告する。差し戻しは「この素材では先へ進めない理由がある」という報告であって、ツールが素材を勝手に直すことではない
- 取り込み後の処理は全て非破壊で、原本は変わらない（A-7、S-11）

#### 6.1.3 Suno 書き出しセットの受け付け

Suno Studio のマルチトラック書き出し（ステム一式とフルミックスを束ねたもの）を、**第一級の入力**として受け付ける。展開したフォルダをそのまま指定すれば取り込める。

- **検出**: 次のパターンを満たすフォルダを「Suno 書き出しセット」と認識する
  - ステムのファイル名が「番号、空白、パート名」の形（例: `1 Woodwinds.wav` 〜 `12 Vocals.wav`）。ステム数は曲によって変わる（最大 12）ので、本数を固定で期待しない
  - 番号 0 で始まる、曲名を持つファイルが同梱されている（フルミックス）
- **役割の割り当て**: 番号ではなくパート名から決める（Woodwinds、Brass、FX、Synth、Strings、Percussion、Keyboard、Guitar、Bass、Drums、Backing Vocals、Vocals を §6.1.1 の語彙に対応させる）。名前が語彙にない場合は `other` とし、推定である旨を記録する
- **フルミックスの扱い**: 番号 0 のファイルはステムとして混ぜず、参照用フルミックス（`fullmix`）として登録する。ステム合算の整合検査と、フルミックス経路のマスタリング（§6.6.1）の入力に使う
- **出所の記録**: 取り込み記録に、検出した入力の種類（Suno Studio のマルチトラック書き出し）、各ファイルの元の名前、内容ハッシュを書く。検出は名前のパターンによる推定なので、その旨も書く
- 検出できなくても取り込みは失敗しない。ただのステム群のフォルダとして扱う
- 書き出しセットを時間整合などで加工した派生セット（ファイル名が変わったもの）も、同じアダプタで同等に受け付ける。派生セットであることは、ユーザーの申告があれば出所に記録する
- 既知の性質（検査で報告されるが、取り込みを妨げない）: 書き出しのレンダリングの尺が元の曲と一致しないことがある。ステムの単純合算がフルミックスに一致しないことがある。ステムにヘッドルームがなく、処理が焼き付いていることがある

他のサービスや DAW の書き出しパターンも、同じ仕組み（名前のパターンと役割の対応表をデータで持つ）で追加できるようにする。

#### 6.1.4 取り込み検査

検査は測定と報告であり、素材を変更しない。

| 検査 | 内容 | 結果の扱い |
|---|---|---|
| 形式 | サンプルレート、ビット深度、チャンネル数、尺。ステム間の不一致 | 記録。不一致は警告（§6.1.5） |
| 無音 | 全サンプルが無音のステム（書き出しの失敗で起きる） | 差し戻し（そのステムを除外するか、取り込みをやり直すかを問う） |
| 健全性 | クリップ、DC オフセット、冒頭のクリックノイズ、NaN | 警告。整音の診断へ渡す |
| ヘッドルーム | ピークとヘッドルーム、過剰なリミッティングの疑い（マスターバス処理済みの疑い） | 警告。処理を始める前にユーザーへ伝える。マスタリングに渡す 2mix は音圧を盛らずヘッドルームを残したものが望ましい、という納品前チェックの考え方による |
| ステム合算の整合 | ステムとフルミックスの両方がある場合、ステムの単純合算とフルミックスの差（ヌルテストの残差と相関）を測る | 記録。§6.6.1 の経路選択の材料。AI 生成サービスのステム書き出しは、合算してもフルミックスに一致しないことがある |
| 重複と欠落 | 同じ内容のファイル、役割が推定できないファイル | 警告 |

#### 6.1.5 尺とサンプルレートが異なる場合

ステム間で尺やサンプルレートが異なっていても、**取り込み時には変換しない**。測定して報告し、レンダリング時にどう扱うかを「変換ポリシー」としてプロジェクトに記録する。

- プロジェクトのサンプルレート: 素材の多数派のレートを既定とする（同数なら高い方）。異なるレートの素材は、レンダリング時にだけリサンプルする
- 尺: 全素材の先頭をそろえる（先頭のサンプルを時刻 0 とする）のを既定とし、短い素材の末尾はレンダリング時に無音として扱う。プロジェクトの尺は最も長い素材に合わせる
- 尺の差が大きい（別テイクや別レンダリングの混在が疑われる）場合は差し戻しとし、位置合わせの方法をユーザーかエージェントに問う。ツールが時間伸縮で勝手に合わせることはしない
- 「差が大きい」の境界: 最も長い素材との差が **0.5 秒、または尺の 0.5% のうち大きい方**を超えたら差し戻し、それ以下なら警告とする。末尾の無音の切り落としによる差は通し、別レンダリングの混在は止めるための値である。境界は `knowledge/` のデータとして持ち、変更できる
- 適用した変換ポリシー（どの素材を、どのレートからどのレートへ、どう位置合わせしたか）は、プロジェクトの正本と Mix Report に記録する
- 以上を既定のポリシーとして確定する（D-054）

### 6.2 ステム分離（任意）

2mix しかない入力、または粗いステムをさらに分けたい場合に使う。

- モデルウェイトは同梱せず、初回利用時に公式配布元から取得する。公式カタログと BYOW の扱いは §12
- 統合層は python-audio-separator（MIT）を土台候補とする。ただし同ライブラリは多数のモデルを自動取得できるため、**レジストリで許可したモデル以外を取得・実行しない**ように包む（S-10）
- 二層構成: 軽量モデルによるプレビュー（CPU でも動く）と、高品質モデルによるバッチ本処理
- 用途別に使い分ける: 目的がボーカル抽出だけなら、4 ステム汎用モデルより 2 ステム専用モデルを使う
- 前処理: 分離に渡す音声は、分離用の一時コピーをおよそ −14 LUFS / ピーク −1 dBFS に正規化する（原本は変えない）
- 後処理の候補: 位相と頭の位置合わせ、キックとベース以外への低域カット、分離で誇張されたシビランスの抑制
- 分離で得たステムには `origin: "separated"` を付ける。分離ステムはブリード（他パートの漏れ）を含むので、エージェントの操作権限を「バランス調整」に制限する（R-22）
- 4 ステムを超える細分化は品質が急に落ちる。細分化の要求には警告を出す
- AI 生成音源は既存モデルの学習分布の外にあり、専用の公開ベンチマークがない。自前の聴感評価セットを用意する（§16.5）

### 6.3 解析

解析は、以降の全ての判断の材料になる測定ベクトル（§4.2）を作る段である。処理はしない。

- **全体**: Integrated LUFS、Short-term 分布、LRA、True Peak、PLR、PSR、LTAS（ERB 帯域）、帯域別相関と Side 比、モノ損失、スペクトルの滑らかさ
- **音楽情報**: BPM、キー、トニック周波数、セクション分割（静かな部分と盛り上がる部分の推定）、拍位置
- **ステム別**: レベル、スペクトル重心、最低基本周波数、倍音比、クレスト、活動区間、推定パン位置と幅、D/R の推定
- **ステム間**: マスキング・リスク（P-02）の行列、低域の同時要素数、キックとベースの基本周波数差
- **AI 生成音源の診断**: 高域の頭打ち周波数、シマー指標、静音区間のノイズ床、冒頭クリック、低中域の密度、Side のアーティファクト（P-16）
- **入力の状態診断**: すでに強くリミットされているか（ヘッドルームと PLR）、ステム合算の整合

解析結果は `analysis` としてプロジェクトの生成物に保存し、素材ハッシュと解析器の版でキャッシュする。解析の主な依存は librosa（ISC）と pyloudnorm（MIT）。

解析の規則:

- 時間パラメータの候補は BPM から音価グリッドで生成する（R-11）
- キーからトニック周波数を求め、「サブ帯域に入るか」「小型スピーカーで消える帯域か」を判定して低域方針の材料にする（R-16）
- 推定値（BPM、キー、役割、主役）には信頼度を付け、低信頼の推定に依存する判断は Mix Report に明示する

### 6.4 整音

AI 生成音源特有のノイズとアーティファクトを、ミックスの前に処理する。マスタリング単体はノイズ床も一緒に持ち上げるので、**順序が本質**である（R-20）。

参照点は、先行実装 Spectral-Lifter（MIT）の方針と、同種ツールに共通する帯域ポリシーである。方針を参照して自前で実装し、取り込む場合はライセンス表示を `third_party/` に残す。

#### 6.4.1 帯域ポリシー（初期値）

| 帯域 | 方針 |
|---|---|
| 〜1 kHz | **無傷**。処理後にクロスオーバーで原音と接合し、ヌルテストで検証する（S-07） |
| 1〜5 kHz | 検出器が判断した箇所だけ処理。主役の明瞭度帯域なので保護を優先 |
| 5〜8 kHz | シビランス帯域。歯擦音と息を守る保護工程を置く |
| 10〜14 kHz | シマー帯域。検出ベースで削減。1回あたり 3〜6 dB の低減量を複数パスで |
| 14 kHz〜頭打ち周波数 | 検出ベースの削減と、最低削減量の設定 |
| 頭打ち周波数より上 | アーティファクトの除去。必要なら高域補完の対象 |

境界と低減量はすべてパラメータで、初期値は較正対象である。

#### 6.4.2 工程

1. **診断**: P-16 を測り、工程ごとに実行／軽減／スキップを決める。決め打ちの一発処理にしない。問題が検出されなければ整音段全体をスキップし、その旨を記録する
2. **クリック修復**: 冒頭などのクリックとポップを局所的に修復する
3. **検出ベースのスペクトル削減**: 帯域ポリシーに従う。信号に相関するノイズを対象にするので、検出にはメロディ追跡、トランジェント起点の解放制御、帯域別スペクトル平坦度を使う
4. **保護**: 歯擦音、息、シンバルの消しすぎを防ぐ
5. **高域補完（任意）**: 削減で失われた、または元から欠落している高域と倍音を補う。**既定は決定的な DSP**（倍音生成に基づく補完）とする。**ニューラルモデルによる補完は標準経路に入れない**（D-041）。ライセンスが確認できたモデルをレジストリ経由で、ユーザーが明示的に有効にしたときだけ使えるオプションとする。有効にした場合は、Mix Report に「生成モデルで高域を補った」と記録する。理由は、本ツールの約束が「実ファイルへの決定的な処理であり、生成で音を作り直さない」こと（§1.2）にあるため
6. **再確認**: 補完で戻ったノイズ、こもり、ピークを測り直す

#### 6.4.3 検証

- **除去分の試聴（delta）**: 「除去した成分だけ」の音声を必ず生成する。人間は試聴で消しすぎを判断でき、エージェントは除去分の中身（主役の歯擦音や息との相関）を測って消しすぎを検出できる。消しすぎなら強度を下げる
- **副作用の測定**（P-21）: ステレオ幅の狭まりと低中域 250〜500 Hz の痩せを測り、許容幅を超えたら強度を下げるか補正する
- **低域無傷の検証**（S-07）
- ステムがある場合はステム単位で整音する（アーティファクトはシンセや FX のステムに集中しやすい）。2mix しかない場合は 2mix に対して行う
- 整音後の P-16 を「ノイズ基準」として保存し、マスタリング後のノイズ戻り監視（§6.7）の比較対象にする

**指揮レイヤーの編集段（任意。2026-11-15 追記）**: 本節の整音とは別に、指揮レイヤーには指揮書で選べる編集 op（`edit_trim`／`edit_gate`、stage `edit`。`docs/DIRECTION_FORMAT.md` §7.1）がある。ステムの内容の無い区間（演奏後の雑音、フレーズ間の漏れ）を、整音前の原素材で検出し、固定の safeguard（EG-1〜EG-5）を通った区間だけを既存の区間ミュート（§9.3 の操作）で無音化する。無音化は整音済み素材の上のクリップで行い、整音器は素材の全長を見続けるので、整音の計画・キャッシュ・S-07／S-08 の基準は編集の有無で変わらない。床の処理経路には入らず、編集 op を書かない指揮書・プロジェクトでは何も起きない。使わなくても不利にならない。

### 6.5 ミックス

#### 6.5.1 順序（固定）

1. **静的バランス**: レベルとパンだけで到達できる最良のバランスを先に作る。プロセッサを使わない（R-04）
2. **アレンジ上の解決**: 衝突が解けない要素は、ミュート、区間の無効化、差し替えを提案する（リミックス操作。§9.3）
3. **引き算の EQ**: 低域カット、問題帯域のカット、競合側を下げるアンマスキング（R-05、R-07）
4. **ダイナミクス**: コンプレッション、ディエッサー、サイドチェイン（時間軸のアンマスキング）
5. **足し算の EQ とエンハンス**: 目的が説明できる場合に限る
6. **空間**: 幅、リバーブ、ディレイ、奥行きの段付け
7. **バス処理**: ミックスバスの軽い処理

各ステップの後に測定し、前のステップで解けた問題を後のステップで触らない。順序を変える場合は理由を Mix Report に残す。

#### 6.5.2 抽象プロセッサ

エージェントとプロジェクト形式が扱うのは、製品名や機種名でなく抽象プロセッサである。内部表現の単位を固定する。

| プロセッサ | 主なパラメータ | 表現の規則 |
|---|---|---|
| `gain` / `pan` | ゲイン dB、パン位置、パン則 | パン則はセンター減衰量の実測で定義し、プロジェクトに明示する（既定 −3 dB）。LCR を含む離散プリセット＋微調整の二層 |
| `filter`（HPF / LPF） | カットオフ、傾斜 | 位相コストを記録する |
| `eq` | 周波数、ゲイン、帯域幅 | 帯域幅は Q でなく**オクターブ幅**で保持する。既定は最小位相。リニアフェーズは位相整合が要る場面に限り、プリリンギングを検証する（R-12） |
| `dynamic_eq` | 上に加えて閾値、時定数 | 問題が間欠的なときに選ぶ（R-13） |
| `compressor` | 閾値、レシオ、ニー、アタック、リリース、検出方式 | 機種名でなく性格ベクトル（検出位置、時定数レンジ、レシオ特性、歪み量）で保持する。時間は音価でも記録する（R-11） |
| `deesser` | 帯域、閾値 | — |
| `saturator` / `clipper` | ドライブ、対称性、帯域 | 倍音の性格（偶数／奇数優位）は測定値で記録する。「真空管＝偶数」のような単純化をハードコードしない |
| `stereo`（幅、M/S、モノメーカー） | 帯域別の Side 量、モノ化境界 | 幅は帯域別ベクトルで扱う。全帯域ワイドナーを既定にしない |
| `reverb` / `delay` | 残響時間、プリディレイ、初期反射／後期の比、ディレイ時間 | プリセット名でなく測定ベクトル（帯域別 RT60、ER/late、D/R）で扱う。時間は音価で記録する。Haas 系は時間域の区分（定位／融合／エコー）を明示し、モノ損失とセットで出す（R-10） |
| `limiter` | 天井、リリース、先読み | True Peak 検出。マスタリング最終段専用 |
| `cleanup.*` | §6.4 の各工程 | — |
| `loudness_gain` / `resample` / `dither` | — | 書き出しモジュール専用 |

各プロセッサは、安定したパラメータ ID、単位、範囲、既定値、実時間処理の可否（§14）を宣言する。

#### 6.5.3 規則の要点

- 評価はステム単体でなく合算後の 2mix に対して行う（R-02）
- 1回の EQ 変更量は原則 ±3 dB 以内、ブーストは広い帯域幅で。超える場合は検証を挟み、理由を記録する（R-06）
- 前に出したい音を上げるより、競合する側の同じ帯域を少し下げる（R-05）
- 低域のカットには必ず「やりすぎの検出」（低域エネルギー総量の下限監視）を対にする（R-07）
- 低域は「全ステムの総和の最適化」でなく「役割の割り当て」として扱う。同時に鳴る低域要素は原則 1〜2 要素（R-08）
- 低域のモノ化は「モノ化せよ」でなく「モノ合算時の損失を測り、閾値を超えたら是正する」（R-09）
- コンプレッサーのゲインリダクションは物差しで説明する（1〜2 dB は軽いまとまり、3〜6 dB は粒をそろえる、10 dB 超は過剰として警告）
- 分離ステムと、処理済みの焼き付いたステム（ヘッドルームがない AI 生成ステム）は、操作量を控えめにする（R-22）
- マスキングが処理で解けないときは、ステム重要度（§4.11）の低い側を下げる・区間をミュートすることを、高い側の極端な加工より優先する。密度が高い編成では、帯域の主役交代（セクションごとの役割分担）を EQ より先に提案する（R-28）
- 一方向の規則には、逆向きの安全弁を必ず対にする（R-29）。こもりを減らす操作は低域総量の下限で止め、刺さりを減らす操作はプレゼンスの下限で止める

#### 6.5.4 歌ものの既定チェーン（雛形）

主役がボーカルの楽曲では、次の5段を既定チェーンの雛形とする。数値は全て [慣行] の初期値で、測定で上書きする。

| 段 | 内容 | 初期値の目安 |
|---|---|---|
| 1 | ボーカルの引き算 EQ と低域カット | 低域カット 80〜100 Hz、こもり帯域 200〜400 Hz、共鳴 2.5〜6 kHz を狭い帯域幅で 2〜4 dB |
| 2 | 2段階のコンプレッション | 速い検出でピークを抑え、遅い検出で 2〜3 dB のレベリング |
| 3 | サチュレーション | 中高域 1〜5 kHz に倍音を足し、小口径の再生でも存在感を保つ |
| 4 | **伴奏側の譲歩** | 伴奏の 1〜3 kHz を 1.5〜2 dB 下げて、声の芯の居場所を作る |
| 5 | リバーブ | プレート系。リバーブ側の低域（600 Hz 以下）と高域（6 kHz 以上）を落とし、余韻だけを残す |

要点は第4段である。ボーカルの音量を上げるだけでは「伴奏の上に歌を乗せただけ」になる。主役を上げるのでなく伴奏に譲らせること（R-05）が、目的関数 `vocal_forward` の対ボーカル P-02 項の直接の根拠になっている。ボーカルの整音（§6.4）は、このチェーンの前に済ませる。

### 6.6 マスタリング

#### 6.6.1 経路の選択

| 経路 | 入力 | 使う場面 |
|---|---|---|
| **ステムミックス経路** | §6.5 のミックス出力 | ステムがあり、再バランスや整音の利益がある。本ツールの中心価値 |
| **フルミックス経路** | 入力の 2mix（整音のみ適用） | ステムがない。または分離ステムの再合算がアーティファクトを累積させると判断される |

ステムの再合算は復元アーティファクトを累積させうるので、分離で得たステムしかない場合の既定はフルミックス経路とし、再バランスの必要が測定で示されたときにステムミックス経路を提案する（R-21）。経路の選択と理由は Mix Report に記録する。

#### 6.6.2 チェーンの順序（固定。S-06）

1. 修正 EQ（共鳴とトーンの修正）
2. 穏やかなダイナミクス制御（既定はシングルバンド。間欠的な問題にはダイナミック EQ、歯擦音にはディエッサー）
3. エンハンス（倍音付加など）
4. ステレオイメージ（低域のモノ整理、上の帯域での幅）
5. ラウドネスの到達（クリッパーは任意）
6. True Peak リミッター（最終段）
7. 書き出し（リサンプル、ディザ。§5.3）

#### 6.6.3 規則

- リミッターは「音圧を上げる装置」でなく「天井」である。マスタリング段を「目標ラウドネスへの到達」でなく「天井とゲインリダクション上限の制約下での到達可能性」として定式化する（R-14）
- リミッターのゲインリダクションが常時 4〜5 dB を超える状態は、ミックス側の問題のサインとして扱い、目標を下げるかミックス段へ差し戻す（P-18。閾値は [慣行]）
- マスタリングで動かす量は小さい。マスター EQ は約 2 dB 以内を初期の上限とする。大きな補正が必要な入力は「ミックスの問題」として検出し、ステムがあればミックス段へ差し戻す（R-15）
- ラウドネスは Integrated の一点でなく、Short-term 最大、LRA、セクション別の値と合わせて扱う。ダイナミックな素材ほど、聴き手の判断は最も大きい瞬間に引きずられるため
- **マスタリング段の既定は、シングルバンドのリミッターと微調整の EQ** とする。理想の 2mix は、シングルバンドのマキシマイザーを薄く掛けるだけで仕上がるものである。マルチバンドのダイナミクス処理は 2mix のバランスそのものを変えられてしまうので、既定のチェーンに入れず、「ミックスへ差し戻す」判断の代替として位置づける。ステムがあるならミックス段で直し、ステムがない（フルミックス経路の）場合に限って、理由を記録したうえで使う（R-30）
- リニアフェーズ EQ をマスタリング段で使う場合は、カット方向の小さな量（約 1 dB まで）に留める
- 音像は「低域ほど中央に集まり、高域ほど左右に広がる」形を基本にする（低域はエネルギーが大きいので中央へ、高域はエネルギーが小さいので広げても破綻しにくい）。`stereo` プロセッサの帯域別の幅の初期値はこの形に従う
- 低域の厚みを守る保護をラウドネス到達の工程に持つ
- セクション間コントラスト（P-20）が処理前より大きく縮んだら警告する

### 6.7 検証

最終出力（出口ごと）に対して行う。合否はすべて実測による。

| 検査 | 内容 | 対応 |
|---|---|---|
| ラウドネス | Integrated LUFS が媒体プロファイルのレンジ内 | P-03 |
| True Peak | 4 倍以上のオーバーサンプリングで測定し、天井以下。条件付き天井（Spotify）も判定 | S-01 |
| コーデック往復 | 想定コーデック（AAC、Opus、MP3 など、使える符号化器）で符号化・復号し、True Peak を再測定 | S-02 |
| ノイズ戻り監視 | マスタリング後の P-16 を整音後の基準と比べる。悪化していたら高域のブースト量やリミッターの駆動を下げる是正案を出す | S-08 |
| 低域と位相 | 帯域別相関、モノ損失 | S-03、S-04 |
| トランスレーション・ゲート | §4.5 の4点 | OF-5 |
| 目的関数の達成度 | 処理前後の代理指標と score の内訳。レベルマッチ後 | §4 |
| 出力の健全性 | NaN、クリップ、DC、尺、形式、ディザの適用記録 | S-05、S-09 |
| 再現性 | 正本からの再レンダリングが同じ結果になる | §16.3 |

使えない符号化器があった場合、その検査は「未実施」と記録し、合格扱いにしない。

### 6.8 Mix Report

全ての測定と判断を文書化して出力する。正本は `report.json`、人間向けに Markdown（および GUI 表示）へ描画する。

構成:

1. **概要**: 入力、目的関数（混合と強度）、媒体プロファイル、出口、総合結果
2. **入力と出所**: 素材一覧、内容ハッシュ、取り込み検査の結果、ユーザー申告の出所、ステム合算の整合
3. **測定（前後比較）**: 代理指標の処理前後。レベルマッチ後の値
4. **判断の記録（6 要素別）**: バランス／定位／周波数／奥行き／ダイナミクス／仕掛け、の6章。各判断は「何を測ったか → どの規則（R-nn）に当たったか → 何をしたか → 検討した代替案 → 結果の測定値」の形で書く
5. **目的関数の達成度**: 指標別の内訳。合計 score だけを出さない
6. **制約とゲート**: S-nn とトランスレーション・ゲートの合否、媒体プロファイルへの適合
7. **整音の記録**: 実行／軽減／スキップした工程、除去量、副作用、ノイズ戻り監視
8. **トレードオフと未解決事項**: 達成できなかった目標、差し戻した問題、弱証拠に依存した判断
9. **人の耳で確認すべき点**: 具体的な試聴ポイントの一覧（時刻と観点つき。例: サビ頭でボーカルの歯擦音が強くないか、モノで低音が痩せていないか、除去分の音声に息や子音が含まれていないか）
10. **再現情報**: プロジェクトの版、エンジンとバックエンドの版、目的関数とプロファイルの定義の版、モデルとライセンスの記録

記述の規則:

- 「仕掛け（Interest）」の章は自動化が最も難しい軸であり、人間の指示とリファレンスに依存すると明示する
- dB 差は知覚倍率（sone 比。+10 dB でおよそ 2 倍）を併記する
- 幅や定位の評価には、前提とした再生系（スピーカー、ヘッドホン、モノ）を書く
- 説明の語彙は知覚語彙辞書（§6.8.1）から引く
- 「人の耳で確認すべき点」には、試聴の条件も書く: 音量を固定して聴くこと、処理前後はレベルマッチ版で比べること、複数の再生環境（モニター、ヘッドホン、スマートフォン）で聴くこと、耳を休めてから最終判断すること（長時間の大音量の後は高域の判断が甘くなる）
- Mix Report の言語は日本語と英語の両方に対応する（D-044）。リポジトリのドキュメントは、private の間は日本語を主とし、公開時に英語の README を主、日本語の README を併置とする。仕様書は日本語のまま置き、英語の概要を添える

#### 6.8.1 知覚語彙辞書

Mix Report の説明と、エージェントが人間の言葉を測定へ結びつけるための辞書。正本は `knowledge/vocabulary.json`。

**使い方の規則**

1. **語彙をそのまま目的関数の名前にしない**。語彙は聞き手の印象のラベルであり、測定可能な代理指標への写像を定義して初めて設計に使える
2. **語彙と数値を必ず対にする**。語彙は「何が起きているか」の要点、数値は「どれだけか」の根拠という役割分担にする（例: 「こもりを抑えるため、伴奏の 250 Hz 付近を 2 dB 下げた。低中域の占有率は 31% から 26% になった」）。語彙だけの説明を出さない
3. **帯域は幅として扱う**。教材によって境界の数値が少しずつ違う（「こもり」は 200〜400 Hz とも 200〜500 Hz とも言われる）。これは誤りでなく、聞き取りの入口としての目安の幅である
4. **各語彙に逆向きの安全弁を対にする**（R-29）。一方向の最適化は必ずどこかを消す
5. **翻訳は直訳しない**。語彙は言語と文化に依存する（日本語の「こもり」と英語の muddy は完全には一致しない）。言語の切り替えは「帯域と現象の組」で対応づける
6. **印象語と音響特徴を一対一に結ばない**。オノマトペと音響特徴の間に系統的な対応があることは研究で示されているが（低い帯域の成分と「濁り・こもり・力強さ」、高い帯域と「鋭さ」など）、印象の属性軸の弁別力は確立しておらず、単純な対応には反例もある。辞書は説明のための語彙であって、評価の軸ではない

**帯域とイメージの早見表**（全て [慣行]。範囲は目安）

| 帯域 | 範囲の目安 | 担うイメージ | 多すぎると | 足りないと |
|---|---|---|---|---|
| サブバス | 25〜60 Hz | 圧力、重み（感じる低音） | ヘッドルームを食う、ボワつく | 軽い、迫力がない |
| バス | 60〜250 Hz | 太さ、土台 | ボワボワ、濁る | 細い、芯がない |
| ローミッド | 240〜500 Hz | ボディ、暖かさ | こもり、モコモコ | ペラペラ、寒い |
| ミッド | 500 Hz〜2 kHz | 芯、前に出る感じ | 箱鳴り、鼻声 | 引っ込む、遠い |
| プレゼンス | 1〜4 kHz | 抜け、明瞭さ | キンキン、刺さる | 埋もれる、こもる |
| ハイ | 4〜6 kHz | 輪郭、歯切れ | エッジがきつい、耳障り | ぼやける |
| エア | 10〜16 kHz | 空気感、きらめき | シャリシャリ、ヒス | 暗い、伸びがない |

|---|---|---|---|---|---|

## 7. エージェントの動作モデル

### 7.1 役割分担

| 担い手 | 役割 |
|---|---|
| 外部エージェント（LLM） | 方針の決定（目的関数とプロファイルの選択、主役の宣言、リファレンスの選択）、計画のレビューと書き換え、Mix Report の要約、人間との対話 |
| プランナー（コア内、決定的） | 測定値と規則から処理計画を作る。候補の評価と反復 |
| DSP エンジン（決定的） | 計画の実行 |
| 人間 | 最終判定（試聴）、意図の指定 |

常駐処理に LLM を使わない。LLM のトークン消費は方針決定とレビューの要所に限る（R-23）。エージェントなしでも、プランナーだけで一通りの処理が完結する（`run` コマンド）。

### 7.2 ループ

```
measure（解析） → plan（計画の提案） → [エージェントまたは人間がレビュー・編集]
   → apply（プロジェクトへ反映） → render（プレビュー） → measure → verify
   → 合格: 次段へ ／ 不合格: 是正案を作って plan へ戻る（反復回数に上限）
```

- プレビューは代表区間（最も大きい区間、静かな区間、主役の入る区間）で行い、最終レンダリングだけ全尺で行う
- 反復には上限を置き、上限に達したら最良の候補と未解決事項を報告する。収束は指標の改善幅で判定し、収束しなければ人間に委ねる
- プランナーとエージェントの出力は、常に「提案」の形を取る（パラメータ、根拠、検討した代替案）。受け取る側の基本操作は「承認して適用する」と「却下して別案を求める」の2つで、これを CLI、MCP、GUI に共通の操作として持つ（R-31）
- エージェントは音を聴けない。エージェント向けの応答は測定値の要約を基本とし、必要に応じてスペクトログラム画像を返す。応答は要約を既定にして、詳細は要求されたときだけ返す（トークン節約）

### 7.3 判断規則

規則は `knowledge/` にデータとして持ち、プランナーが参照し、Mix Report が ID で引用する。エージェントは規則を参照できる（§10.3 の `knowledge_lookup`）。

| ID | 規則 | 型 |
|---|---|---|
| R-01 | 比較と判断はレベルマッチ後に限る。マッチ前の帯域過不足の断定を禁止する | 判断規則 |
| R-02 | 帯域評価は ERB / Bark 軸で行う。ステムはフルミックス文脈で評価する | 判断規則 |
| R-03 | 想定する再生レベルと再生系を宣言してから、帯域バランスと幅を判断する。宣言がなければ低域判断の信頼度を下げる | 判断規則 |
| R-04 | 修正は「静的バランス（レベル、パン）→ アレンジ（ミュート、差し替え）→ 処理」の順に提示する | 判断規則 |
| R-05 | ブーストよりカットを優先する。主役を上げる前に競合側を下げる | 判断規則 |
| R-06 | 一手は小さく。EQ は原則 ±3 dB 以内、マスター EQ は約 2 dB 以内。超える場合は検証を挟み理由を記録する | prior |
| R-07 | 低域カットは楽器の最低基本周波数の直下に置く。低域エネルギー総量の下限監視を対にする | 判断規則 |
| R-08 | 低域は役割の割り当てとして扱う。同時の低域要素は原則 1〜2 | prior |

| R-10 | Haas 系の幅出しは時間域の区分を明示し、モノ損失とセットで出す | 判断規則 |
| R-11 | 時間パラメータ（リリース、プリディレイ、ディレイ）は ms でなく音価で推論・記録する。ゲインリダクションの回復率を波形で検証する | 判断規則 |
| R-12 | EQ の既定は最小位相。帯域幅はオクターブ幅で保持する | 判断規則 |
| R-13 | 間欠的な問題にはダイナミック処理、常時の問題には静的処理 | 判断規則 |
| R-14 | リミッターは天井。ゲインリダクションが常時大きいならミックスへ差し戻す | 判断規則 |
| R-15 | マスタリング段で大きな補正が必要なら、ミックスの問題として差し戻す | 判断規則 |
| R-16 | キーからトニック周波数を求め、低域方針（基本音の活用／倍音補完）を切り替える | 判断規則 |
| R-17 | ジャンル目標は固定閾値でなくリファレンス実測分布からの相対偏差で持つ。Harman カーブをミックスの目標に流用しない | 判断規則 |
| R-18 | 媒体のラウドネス値は配送条件であり、音作りの目標ではない。音圧競争の項を置かない | 判断規則 |
| R-19 | ディザは深度削減時のみ、最終段で1回だけ | 安全不変条件（S-05） |
| R-20 | 整音はミックスとマスタリングの前。マスタリング後にノイズ戻りを監視する | 安全不変条件（S-08） |
| R-21 | マスタリング経路（ステムミックス／フルミックス）を、ステムの出自と合算の整合から選ぶ | 判断規則 |
| R-22 | 分離ステムと焼き付いたステムは「外科手術」でなく「バランス調整」に使う。操作量を制限する | prior |
| R-23 | LLM は方針決定とレビューに限る。常駐処理は決定的ロジック | 設計原則 |
| R-24 | 最終判定は人の耳。試聴ポイントを必ず出す | 設計原則 |
| R-25 | レベル差の説明には知覚倍率を併記する | 判断規則 |
| R-26 | 展開のコントラスト（静と動、ピーク前の開き方）を平坦化しない | 判断規則 |
| R-27 | 圧縮量の正解は一律でない。騒音環境対策としての過圧縮は根拠が弱いので既定にしない | prior |
| R-28 | マスキングが処理で解けないときは、ステム重要度の低い側を下げる・ミュートすることを、高い側の極端な加工より優先する。帯域の主役は 1〜2 個までとし、密度が高ければ主役交代を先に提案する | 判断規則／prior |
| R-29 | 一方向の規則には、逆向きの安全弁を必ず対にする（こもりを減らすなら低域総量の下限、刺さりを減らすならプレゼンスの下限） | 判断規則 |
| R-30 | マスタリング段の既定はシングルバンド。マルチバンドのダイナミクスは、ミックスへ差し戻す判断の代替としてのみ使う | prior |
| R-31 | 出力は常に、根拠と代替案を伴う提案の形にする。基本操作は「承認して適用」と「却下して別案」 | 設計原則 |
| R-32 | 入力は無加工のまま受け取る。取り込み検査の差異は警告か差し戻しとし、強制変換の理由にしない | 設計原則（A-12） |
| R-33 | ジャンルの慣行は重みと目標範囲の初期値にだけ使う。リファレンスの実測とユーザーの指定が常に優先する | prior |

## 8. 知識基盤から設計ルールへの対応

本章は、設計の根拠となった知識と、それが仕様のどこに変換されたかの対応表である。変換の型は4つ: **代理指標化**、**判断規則化**、**安全不変条件**、**prior 化**。

### 8.1 心理音響・音響学

| 知識 | 変換先 | 型 |
|---|---|---|
| 等ラウドネス曲線（ISO 226）。感度は 2〜5 kHz で最大。レベルが下がると低域と高域が相対的に聞こえにくくなる | P-01 の知覚重み、P-11、R-03、OF-5 の小音量チェック | 代理指標化、判断規則化 |
| 臨界帯域と ERB。帯域内のエネルギーは分離せず合算される | 評価軸を ERB にする（R-02）、P-02 | 代理指標化 |
| 上方拡散マスキング。低い音は高い音を覆いやすく、大音量ほど広がる | P-02 の拡散関数、OF-1 の低域発マスキング項、R-08 | 代理指標化 |
| 時間マスキング。大きな音の後 100〜200 ms は細部が聞こえにくい | コンプレッサーのリリース設計とリバーブ量の根拠、P-12 | 判断規則化 |

## 9. プロジェクト形式（JSON 正本）

### 9.1 構成

プロジェクトは1つのフォルダである。

```
<name>.mmx/
├─ project.json        正本。これだけで処理内容が再現できる
├─ journal.jsonl       操作履歴（追記のみ）
├─ assets/             取り込んだ素材（原本。変更しない）
├─ analysis/           解析結果（再生成可能）
├─ renders/            レンダリング結果（再生成可能）
├─ reports/            Mix Report（再生成可能）
└─ cache/              中間生成物（再生成可能）
```

- **パスは全てプロジェクトフォルダからの相対パス**。絶対パスを正本に書かない。素材は内容ハッシュで同定する
- 素材を外部に置いたまま参照する「リンク素材」も許すが、その場合も正本には論理名とハッシュだけを書き、実際の場所は正本の外（ユーザーのローカル設定）で解決する
- `analysis/` `renders/` `reports/` `cache/` は正本と素材から再生成できるので、バージョン管理や共有の対象にしなくてよい
- 正本は JSON Schema（`schemas/project.schema.json`）で検証する。`schema_version` を持ち、版が上がったときは移行処理を提供する

### 9.2 正本の骨子


### 9.3 リミックス操作

ステム単位の差し替え・追加・再配置を、正本への操作として定義する。

| 操作 | 内容 |
|---|---|
| ステムの追加 | 新しい素材を取り込み、トラックを追加する（別素材の楽器を足す） |
| ステムの差し替え | トラックの参照素材を別の素材に替える。処理チェーンは保持するか選べる |
| 区間の無効化 | クリップを分割し、使えない区間をミュートする |
| 区間の差し替え | 無効化した区間に別の素材のクリップを置く |
| 再配置 | クリップのタイムライン上の位置を動かす |
| 役割と主役の変更 | `role` と `is_lead` の変更 |
| ステムの再書き出し | 処理後のステムを個別に書き出す（リミックス用、DAW へ戻す用） |

- 追加・差し替えた素材は、取り込み検査（§6.1）とテンポ・キーの整合診断を受ける。ずれは報告する
- **タイムストレッチとピッチシフトは v1 の範囲外**で確定する（D-048）。定番の実装が GPL で使えず、採用できるライセンスの実装が未調査のため。テンポやキーが合わない素材は、ずれを報告するに留める。寛容ライセンスの実装の調査は M10 で行う
- MIDI などの構造化データを扱う拡張点として、トラックに `kind`（`audio` が既定）を予約する。**v1 は `audio` のみ**で確定する（D-051）

### 9.4 バリアント

一つのプロジェクトから、目的関数や出口が異なる複数の仕上げを作る。バリアントは「目的関数の上書き」「マスタリング経路とチェーン」「出口の一覧」を持つ。ミックスまで変えるバリアントは、トラックのパラメータに対する差分として持つ。

### 9.5 操作履歴

- 正本への全ての変更は、操作として `journal.jsonl` に追記する（誰が＝人間／エージェント／プランナー、何を、なぜ）
- 取り消しと任意時点への復帰を提供する
- GUI と CLI / MCP が同じプロジェクトを同時に開いている場合、正本の変更を検知して再読込する。同時編集の衝突は「後から書いた側が、最新の正本に対する操作として再適用する」方式とし、適用できない場合は失敗を返す

### 9.6 レンダリング記録と再現性

レンダリングごとに記録（manifest）を残す: 正本のハッシュ、素材のハッシュ、エンジンの版、使用したバックエンドとその版（FFmpeg は版とビルド構成）、モデルの ID とハッシュ、目的関数とプロファイルの定義の版。

再現性の約束: **同じ正本、同じ素材、同じエンジンの版、同じバックエンドの版なら、同じ出力になる**。プラットフォームをまたぐ場合はビット一致でなく許容誤差内の一致とする（§16.3）。乱数を使う処理（TPDF ディザなど）は、正本から決まる固定の種を使う。

## 10. CLI と MCP

### 10.1 共通方針

- CLI と MCP は、コア API を 1 対 1 で包む。片方にしかない機能を作らない
- 全コマンドは機械可読な JSON 出力を持つ。終了コードで成否を区別する（成功、検証不合格、入力エラー、環境エラー）
- 破壊的な操作はない（原本不変、正本は履歴で復帰可能）
- 出力に絶対パスを含めない設定を既定にする（プロジェクト相対で返す）

### 10.2 CLI コマンド体系

コマンド名は `mankomix`。同じコマンドを短縮名 `mmx` でも呼べるようにする（D-044）。ドキュメントと例は `mankomix` で書く。

| グループ | コマンド | 内容 |
|---|---|---|
| 環境 | `doctor` | 依存の検査。FFmpeg の有無とビルド構成（GPL 部品や nonfree が有効でないか）、使える符号化器、GPU、モデルの状態 |
| プロジェクト | `init` / `import` / `status` / `validate` | 作成、素材の取り込み（アダプタ指定）、状態、正本の検証 |
| ステム | `stem list` / `add` / `replace` / `remove` / `move` / `mute` / `role` / `export` | リミックス操作（§9.3） |
| 分離 | `separate` | モデル指定、プレビュー／本処理 |
| 解析 | `analyze` / `measure` / `compare` | 解析の実行、任意の音声の測定、2つの音声のレベルマッチ比較 |
| 意図と出口 | `objective list` / `show` / `set` / `validate`、`profile list` / `show`、`reference add` / `list` / `remove` | 目的関数、媒体プロファイル、リファレンス |
| 段の処理 | `clean plan` / `apply` / `delta`、`mix plan` / `apply`、`master plan` / `apply` | 段ごとの計画の提案と適用。`delta` は除去分の音声を書き出す |
| 編集 | `set` / `patch` | 正本のパラメータ変更（スキーマ検証つき） |
| レンダリング | `render` / `export` | プレビュー（区間指定）、出口ごとの最終書き出し |
| 検証 | `verify` / `report` | 検証の実行、Mix Report の生成（JSON / Markdown） |
| 一括 | `run` | 取り込みから検証とレポートまでを、プランナーだけで一通り実行する |
| 履歴 | `history` / `undo` / `checkout` | 操作履歴 |
| モデル | `model list` / `show` / `pull` / `register` / `verify` / `remove` | レジストリ（§12） |
| 顔 | `serve` / `mcp` | GUI 用のローカルサーバー、MCP サーバー |

一括実行の例:

```
mankomix run ./stems --objective comfort --profile spotify --delivery distributor_44k16 --out ./out
mankomix run ./stems --objective bass_heavy:0.7 --profile club --out ./out
```

### 10.3 MCP ツール

MCP サーバーは標準入出力で起動する（`mankomix mcp`）。ツールは CLI と同じ粒度で、名前は `グループ_動詞` の形にする。

| ツール | 内容 |
|---|---|
| `project_open` / `project_get` / `project_patch` / `project_validate` | 正本の取得と変更。変更はスキーマと不変条件で検証する |
| `import_files` | ファイル入力アダプタでの取り込み |
| `stems_list` / `stems_add` / `stems_replace` / `stems_edit` / `stems_export` | リミックス操作 |
| `separate_run` | ステム分離 |
| `analyze_run` / `measure_audio` / `compare_audio` | 解析、測定、レベルマッチ比較 |
| `objective_list` / `objective_get` / `objective_set` | 目的関数 |
| `profile_list` / `profile_get` | 媒体プロファイル |
| `reference_add` / `reference_list` | リファレンス |
| `plan_propose` / `plan_apply` | 段（整音／ミックス／マスタリング）ごとの計画の提案と適用 |
| `render_preview` / `render_spectrogram` / `export_run` | プレビュー、スペクトログラム画像、最終書き出し |
| `verify_run` / `report_get` | 検証と Mix Report |
| `model_list` / `model_pull` / `model_register` | モデルレジストリ |

- 応答は要約を既定にし、詳細度を引数で指定できるようにする
- 時間のかかる処理（分離、全尺レンダリング）は、ジョブ ID を返して進捗を問い合わせる形にする
- MCP サーバーがアクセスできる範囲は、起動時に指定した作業フォルダの中に限る
- 外部サービスの MCP（Suno など）には依存しない。連携は将来、入力アダプタとして追加する

## 11. GUI と Pages デモ

### 11.1 方針

- GUI は人間向けの顔であり、コア API の上に載る。GUI にしかない処理ロジックを持たない
- **レスポンシブ**であること（スマートフォン幅からデスクトップ幅まで）
- GUI はバックエンド接続をインターフェースで抽象化し、2つの実装を持つ

| 実装 | 接続先 | 用途 |
|---|---|---|
| ローカル接続 | `mankomix serve` のローカルサーバー | 通常利用。全機能 |
| デモ用モック | ブラウザ内のモックバックエンド | GitHub Pages のデモ。UI は同一 |

### 11.2 画面

| 画面 | 内容 |
|---|---|
| プロジェクト | 作成、素材の取り込み、取り込み検査の結果、出所の記録 |
| ステム | トラック一覧、レベル、パン、ミュート、ソロ、役割と主役、クリップの編集（リミックス操作） |
| ミックスマップ | 各ステムを「左右＝パン、上下＝スペクトル重心、大きさと濃さ＝奥行き」で配置した図。重なり＝マスキングの警告を表示 |
| 解析 | 測定ベクトルの表示。LTAS とリファレンス分布、帯域別相関、ラウドネスの時系列、AI 生成音源の診断 |
| 意図と出口 | 目的関数の選択・混合・強度、主役の宣言、リファレンス、媒体プロファイルと納品形式 |
| 計画 | プランナー（またはエージェント）が提案したチェーンの確認と編集。各処理に理由（規則 ID）を表示。提案は全て編集できる |
| 試聴 | 処理前後の A/B。**レベルマッチを標準**にし、切り替え可能にする。除去分（delta）の試聴、モノ、帯域制限、小音量相当のプレビュー |
| 検証 | 制約、ゲート、媒体プロファイルへの適合、ノイズ戻り監視、コーデック往復の結果 |
| Mix Report | レポートの閲覧と書き出し |
| モデル | レジストリの一覧、ライセンス表示、取得、BYOW 登録 |
| 履歴 | 操作履歴。誰が（人間／エージェント／プランナー）何をしたか |

- 外部エージェントが CLI / MCP 経由で正本を変更したら、GUI は変更を検知して表示を更新する。人間とエージェントが同じプロジェクトを見ながら作業できる
- **GUI の「エージェント機能」とは、外部エージェントとの連携のことである**（D-035）: 外部エージェントが CLI / MCP 経由で行った操作を GUI が表示・追従すること、履歴画面で誰が何をしたかを示すこと、エージェントの提案を GUI で承認・却下すること
- **v1 の GUI は、LLM と対話するパネルを内蔵しない**。API キーの保管と LLM への通信を GUI に持ち込まないためで、コア自身が LLM を呼ばない原則（A-3）とも揃う。対話は、利用者が普段使っているエージェント（MCP クライアント）の側で行う
- コア内の決定的なプランナーは「エージェント機能」に含めない。LLM を使わない自動処理であり、GUI から直接呼べる

### 11.3 レスポンシブの要件

- 狭い幅では、ステム一覧は1列のカード、ミックスマップと解析は縦積み、試聴の操作は画面下部に固定する
- 試聴（A/B の切り替え、レベルマッチの切り替え）と Mix Report の閲覧は、スマートフォン幅で完全に使えること
- 細かい編集（クリップ編集、チェーン編集）は、狭い幅では閲覧を主とし、編集は簡略化してよい

### 11.4 Pages デモ

- GitHub Pages で、**エージェント機能を除いた形**で試せるデモを公開する。除くのは、外部エージェントとの連携（操作の追従、提案の承認と却下、エージェントの操作履歴の更新）である。決定的なプランナーの結果は、事前に計算したものとして見せる
- UI は本体と同一。バックエンドがブラウザ内モックに差し替わる
- モックは、公式サンプル（§15）について事前に計算した解析結果、計画、Mix Report、事前にレンダリングした音声（処理前、処理後、除去分、レベルマッチ版）を返す
- デモでできること: 画面の閲覧、目的関数と媒体プロファイルの切り替え（事前に用意した組み合わせの範囲）、A/B 試聴、Mix Report の閲覧
- デモでできないこと: 任意の音声の取り込み、実際の DSP 処理、エージェント連携、モデルの取得。できないことは画面上に明示する
- デモ用の事前計算データは、本体のコアで生成するビルド手順を用意し、手書きしない（本体とデモの乖離を防ぐ）
- デモは外部へ通信しない。利用者の音声をアップロードする経路を持たない
- ブラウザ内で実際の DSP を動かす（ネイティブ核の WebAssembly 化）は将来の拡張とする

### 11.5 テーマとアイコン（確定。D-067）

- GUI のテーマは、同じオーナーの製品 CyberSprite と同じ製品ファミリーのテーマ **「Circuit White」（C 案 "Solder Mask"、CyberSprite SPEC §14.3）** にする。白と水色の回路基板の世界観（白い基板、水色の配線の枠、面取りしたパッド、切り替えた要素の「通電」表示）を揃える
- 色の正本は CyberSprite の `gui/src/theme/tokens.css` のベーストークン（`--cs-*`）。`gui/src/theme/tokens.css` に同じ内容を**そのまま**取り込む（「verbatim」の区画。直さずに丸ごと複写し直して更新する）。部品は色を直接持たず、**役割トークン**を参照する: ファミリー共通の役割（`--ui-*`、CyberSprite と同一）と、MankoMIX 固有の役割（`--mm-*`）。`styles.css` とコンポーネントに生の色値を書かない（`src/test/theme.test.ts` で検査）
- MankoMIX 固有の役割トークンは、新しい色を足さず、ベーストークンかファミリーの役割トークンへの参照だけで定義する。追加したものの一覧は `tokens.css` の注記にある（ページ、面、強調、Before / After の系列、リファレンス帯、波形、ミックスマップのステム、検証の合格・不合格・警告・未実施、メーター、マスキングの線、エージェントとプランナーの印、合成データの印、図の格子と軸）
- 状態は色だけで伝えない（CyberSprite SPEC §14.3.3 と同じ制約）: 検証の合否はアイコン（validate-ok / error / warning）と文字、図の Before は破線、注意と誤りは三角と八角形の形を併用する。文字色に水色を使わない。テーマは明色だけで、暗色版は持たない（ファミリーのテーマに無いため）
- アイコンは 16×16 のピクセルアートで、CyberSprite の共通パレット ui-icons（11 色）だけを使う。意味が合うものは CyberSprite のアイコンを複写して使い回し（トランスポート、folder、add、remove、lock、link、info、error、warning、validate-ok、agent、human、grid、undo、settings、sources）、MankoMIX 固有のもの（waveform、stem、separate、export、download、headphones、meter、report、model、chain）は同じ流儀（1px の濃紺の輪郭、意味は形で伝える）で新しく描く。新しいアイコンの画素は `tools/make_icons.py` の設計データを CyberSprite の CLI（`draw_rows`、`validate`、`export image`）で書き込む（CyberSprite が自分のアイコンを作るのと同じ経路）
- 来歴は `gui/public/icons/manifest.json`（アイコンごとの出所、元のファイル名、ライセンス、SHA-256）と `NOTICE` に記録する。絶対パスと個人情報は書かない（§16.4）。`python -I tools/make_icons.py check` で、パレット、大きさ、設計との一致、来歴を検査する（標準ライブラリだけで動く）
- 文字のある操作に添えるアイコンは装飾（代替テキストなし）とし、アイコンだけの操作と表示には読み上げ用のラベルを付ける

## 12. モデルレジストリとライセンス運用

### 12.1 原則

1. **モデルウェイトは同梱しない**。初回利用時に、ユーザーの環境へ公式配布元から取得する
2. **公式カタログに載せるのは、使用と再配布の両方がライセンス上クリーンなウェイトだけ**
3. 使用目的そのものを縛るライセンス（研究目的限定、非商用）のウェイトは、ダウンロード式でも標準経路に入れない
4. 代わりに **BYOW**（ユーザーが自分で取得したウェイトを登録する口）を用意する。その範囲のライセンス確認はユーザーの責任と明示する
5. **ライセンスメタデータのないエントリは、レジストリの検証を通らない**（公式カタログも BYOW も同じ）
6. コードのライセンスとウェイトのライセンスは別物として記録する

### 12.2 レジストリのエントリ

```json
{
  "id": "example_vocals_2stem",
  "task": "separation",
  "stems": ["vocals", "instrumental"],
  "architecture": "mel_band_roformer",
  "runtime": { "backend": "audio_separator", "min_vram_gb": 6, "cpu_ok": false },
  "weights": {
    "source_url": "https://example.invalid/official-distribution/model.ckpt",
    "sha256": "…",
    "size_bytes": 0
  },
  "license": {
    "code": "MIT",
    "weights": "MIT",
    "usage_restrictions": "none",
    "evidence": [{ "url": "https://example.invalid/license-evidence", "checked_on": "2026-11-13", "note": "author statement" }],
    "caveats": ["training data terms may apply; legally unsettled"]
  },
  "attribution": "credit text to display",
  "tier": "official",
  "status": "draft"
}
```

- `tier`: `official`（公式カタログ）または `byow`
- `license.weights` と `license.evidence` は必須。根拠（著者の声明、モデルカード、ライセンスファイル）の URL と確認日を持つ
- `usage_restrictions` が `none` 以外のエントリは `official` にできない
- ウェイトは配布元から直接取得し、ハッシュで検証する。本プロジェクトのサーバーでミラーしない
- 取得時に、ライセンス、帰属表示、留保事項を表示する
- 使用したモデルとライセンスは、レンダリング記録と Mix Report に残す

### 12.3 公式カタログの候補

実装フェーズで、各エントリの根拠を一次資料で再確認してから `official` にする。現時点の候補と判定:

| 候補 | 用途 | ウェイトのライセンス（調査時点） | 扱い |
|---|---|---|---|
| Kim Mel-Band RoFormer（ボーカル 2 ステム） | 高品質のボーカル分離 | MIT（著者が再ライセンスを明言） | 公式カタログ候補・本命 |
| SCNet / SCNet-large（4 ステム） | 軽量。プレビューと CPU 実行 | MIT（著者確認ありとの監査記録） | 公式カタログ候補 |
| Open-Unmix umxhq（4 ステム） | 控え。品質は割り切る | MIT | 公式カタログ候補（予備） |
| UVR チーム製 MDX-Net 系 | 2 ステム、カラオケ補助 | MIT（クレジット表示が条件） | 候補。帰属表示を必須にする |
| Demucs 公式ウェイト | — | 著者が研究目的限定と明言 | **標準経路に入れない**。BYOW のみ |
| Open-Unmix umxl | — | CC BY-NC-SA | **標準経路に入れない**。BYOW のみ |
| ライセンス無宣言のコミュニティ製チェックポイント | — | 公表なし | **標準経路に入れない**。BYOW のみ |

- 留保: 多くのモデルの学習データ（MUSDB18）は教育・研究用途のデータセットであり、その条件が学習済みウェイトに及ぶかは法的に未確定である。この留保をレジストリの `caveats` に記録し、ユーザーに表示する
- 品質の天頂（ライセンス無宣言のモデルを含むアンサンブル）は、配布せず、内部ベンチマークの目標としてのみ持つ
- 要確認リスト（実装フェーズで潰す）: 一部の配布元のチェックポイントの同梱・取得可否、ドラム内部分離モデルのライセンス、音源復元（帯域拡張）モデルのライセンス

### 12.4 BYOW

- ユーザーがウェイトファイルと設定を指定して登録する。登録時にライセンス欄の入力を必須にする（不明なら「不明」と明示して登録できるが、警告を出し、Mix Report に記録する）
- BYOW の登録情報はユーザーのローカル設定に保存し、プロジェクトの正本にはモデルの ID とハッシュだけを書く
- ツールは BYOW のウェイトを取得・再配布しない

## 13. 依存とライセンス方針

### 13.1 方針

- 本体は Apache-2.0。取り込めるのは MIT / BSD / ISC / Apache-2.0 のコードだけ
- **GPL / AGPL のコードと文章は持ち込まない**。手法の参考に留める
- LGPL のものは、外部プロセスとして呼ぶ分離を前提にする
- ライセンスが未確認（NOASSERTION など）のものは、実物のライセンス文を確認するまで採用しない
- 取り込んだ第三者コードは `third_party/` に置き、ライセンス文と出所を併記する

### 13.2 採用候補と不採用

| 区分 | 対象 | ライセンス | 扱い |

### 13.3 FFmpeg の扱い

FFmpeg の扱いを次のとおり確定する（D-043）。

- **本プロジェクトは FFmpeg を同梱も再配布もしない**。ユーザー環境の FFmpeg を、外部プロセスとして呼ぶ
- **標準経路が使うのは、LGPL 構成のビルドに含まれる機能（フィルタ、符号化器）だけ**とする。GPL 構成でしか使えない部品に依存する処理を書かない。これにより、処理結果がビルドの種類に左右されず、LGPL 構成のビルドだけで全機能が動く
- 推奨し、ドキュメントで入手を案内し、CI で使うのは LGPL 構成のビルドとする
- **ユーザーの FFmpeg が GPL 構成のビルドであっても、実行は止めない**。広く配布されているビルドの多くが GPL 構成であり、止めると大半の環境で動かなくなるため。外部プロセスとして呼ぶだけなので、本体のライセンスには影響しない。その場合は `doctor` が警告を出し、ビルド構成をレンダリング記録と Mix Report に残す
- LGPL 構成以外を拒否したい利用者のために、厳格モード（LGPL 構成でなければ実行しない設定）を用意する。既定は無効
- nonfree が有効なビルドは、厳格モードでなくても警告を強くする（再配布できないビルドであるため）。本プロジェクトがそのバイナリを配ることはない
- FFmpeg の自動取得は行わない
- `doctor` と起動時検査が、FFmpeg の版、ビルド構成、使える符号化器を調べる。ビルド構成はレンダリング記録に残す
- コーデック往復の検査に使う符号化器は、そのビルドで使えるものに限る。使えなければ「未実施」と記録する

### 13.4 監査

- 依存のライセンス一覧を自動生成し、許可リストにないライセンスが入ったら CI を落とす
- レジストリの検証（ライセンスメタデータの必須項目）を CI で行う
- 公開前に、ライセンスと衛生の監査を独立した工程として行う（§17 の M8）

## 14. プラグイン化（VST 等）への考慮

### 14.1 方針

将来、DSP エンジンをプラグインシェル（VST3 など）で包めるように、今から構造を分ける。プラグインの実装は今回の範囲外で、採用する形式とフレームワークは確定しない。

### 14.2 構造上の約束

| 約束 | 内容 |
|---|---|
| 核の独立 | ネイティブ DSP 核は、UI、ファイル入出力、ネットワーク、エージェント層に依存しない。入出力はサンプルバッファとパラメータだけ |
| 共有契約 | プロセッサグラフの JSON 記述（チェーン）を、オフラインレンダラとプラグインの共通の状態表現にする。プロジェクトで決めたチェーンを書き出し、プラグインが読み込める |
| パラメータ | 各プロセッサのパラメータは安定した ID、単位、範囲、既定値を持つ。版をまたいで ID を変えない |
| 実時間適性の宣言 | プロセッサごとに、ブロック処理の可否、レイテンシ、処理中のメモリ確保の有無を宣言する。スペクトル整音のようなオフライン専用の処理は、その旨を宣言する |
| 解析とエージェントは外 | 解析、目的関数の評価、プランナー、エージェント連携は、プラグインの中でなくコンパニオン（本体）側に置く |

想定する最初のプラグインの姿は「本体で決めたマスタリングチェーン／ミックスチェーンを DAW の中で再生・微調整するチェーンプレイヤー」である。

### 14.3 検討事項と確認タスク

| 項目 | 状態 |
|---|---|
| VST3 SDK のライセンス条件 | **確認済み**（D-063）: SDK 3.8 以降は MIT。3.8 以降の SDK だけを使い、VST2 のヘッダ、ASIO SDK、AAX SDK は使わない。一次資料は `docs/PUBLICATION_AUDIT.md` §3 |
| JUCE | 調査時点で GPL 系と商用のデュアルライセンスと認識しており、Apache-2.0 と両立しない。商用ライセンスを買う判断をしない限り採用しない。現行条件を一次資料で確認する |
| 他の候補（CLAP など、寛容ライセンスのプラグイン規格やフレームワーク） | 確認済み（D-063）: CLAP は MIT、LV2 は ISC、AudioUnitSDK は Apache-2.0 |
| プラグイン本体のライセンスと配布形態 | 本体と同じ Apache-2.0 で配れる形式とフレームワークだけを採用する。できない形式は採用しない |
| 対応形式と優先度、着手時期 | 確定（D-049）: プラグイン化は **v1 の公開の後**に着手する。M10 で実現可能性を調査し、第一候補は寛容ライセンスの規格（CLAP）、VST3 は SDK のライセンス条件を一次資料で確認できた場合に対応する。**JUCE は採用しない**（商用ライセンスを買わない）。D-063 で VST3（SDK 3.8 以降）の条件は満たされた |

確認が終わるまで、ネイティブ核はどのプラグイン SDK のヘッダにも依存させない。

### 14.4 プラグインの GUI（将来フェーズの要件。D-067）

- プラグイン化（§14.3、D-049 / D-063 の線。CLAP が第一候補）で作るシェルの GUI も、本体の GUI と同じ製品ファミリーのテーマ（§11.5 の「Circuit White / Solder Mask」、同じベーストークンと役割トークンの構造）と、共有アイコンセット（ui-icons パレットの 16×16）で設計する
- 今のフェーズでは実装しない。プラグインのフェーズに入るときの要件として記録するだけである

## 15. サンプル素材と README の方針

### 15.1 公式サンプル

- 公式サンプル楽曲は「マンコ主義」（オーナー決定）。使うのは、Suno Studio のマルチトラック書き出しで得た公式ステムである
- **サンプルの正本は、原曲の尺に時間整合させた conform 済みセット**とする（48 kHz、ステム 12 本と、整合済みのフルミックス）。BRIEF の基本方針に従ってこれを確定とする
- conform 済みセットを正本にする理由: (1) 実際の制作で使われた版である、(2) 原曲と尺が一致しており、原曲との比較ができる
- サンプル素材のローカルでの所在は、リポジトリの外（`_private/`）にのみ記録する

**原本と派生物の区別**（オーナー追加要件による確定。D-031）

| セット | 位置づけ | 内容 |
|---|---|---|
| **書き出しセット** | **原本**。Suno Studio からダウンロードしたままのファイル群 | 最大 12 ステムの WAV（48 kHz、書き出し時のレンダリングの尺）と、同梱のフルミックス。ファイル名は「番号、空白、パート名」の形 |
| **conform 済みセット** | 書き出しセットを原曲の尺に時間整合させた**派生物**。README の聴き比べに使うサンプルの正本 | ステム 12 本と整合済みのフルミックス（48 kHz） |

conform 済みセットのフォルダには、ステム 12 本のほかに `other` と `no_vocals` という2つのファイルがある。素材側の制作記録を確認した結果、どちらも Suno のステムではなく、**ステムを合算して作った派生ファイル**であることが分かった（`other` はボーカル、ドラム、ベース以外の 8 ステムの合算、`no_vocals` はボーカル以外の合算）。したがって、**この2つは公式サンプルの入力に含めない**（D-037）。含めると同じ音を二重に足すことになる。公式サンプルの入力は、書き出しセットと同じ 12 ステムとフルミックスである。

- ワークフローは、**書き出しセットも conform 済みセットも同等に受け付ける**。書き出しセットは、ダウンロードして展開したフォルダを、変換もリネームもせずそのまま入力にできる（§6.1.2、§6.1.3）
- したがって「Suno から書き出したままのステムを、そのまま本ツールに入れられる」は製品の約束であり、公式サンプルの書き出しセットでこれを実証する。回帰テストは両方のセットを入力として持つ（§16.2）
- README の聴き比べは conform 済みセットで作る（正本の方針は維持）。README には、書き出しセットをそのまま入力にできることと、聴き比べに使ったのが時間整合済みの派生セットであることを、両方書く
- 留意点: conform は時間整合の加工を経ている。また、ステムの単純合算は同梱のフルミックスと一致しない（取り込み時の整合検査で大きな残差が出る）。これは AI 生成サービスのステム書き出しの性質であり、本ツールの検査機能（§6.1.4）の実例として Mix Report に表れる
- 公式サンプルに宣言するジャンルは **`hiphop`**（ヒップホップ／ラップ楽曲であるため。D-053）。リファレンス曲は登録せず、汎用の目安とジャンル prior で処理し、その旨を Mix Report に書く（D-039）

### 15.2 聴き比べの定義（確定。D-036、D-040）

README に、何もしていない音声と、本ツールで加工した音声を聴き比べられる形で置く。

| 音声 | 定義 |
|---|---|
| **処理前（Before）** | **12 ステムの単純合算**（各ステムをゲイン 0 dB、ステレオのまま加算。処理なし）。本ツールへの入力と完全に同じ素材から作られるので、処理後との差が本ツールの処理だけに由来する |
| 参考: 既存フルミックス | サービスが書き出したフルミックス（整合済み）。「何もしない場合に手元にある音」としての参考。ステムの合算とは一致しないので、処理前の基準にはしない |
| **処理後（After）** | 本ツールの出力。下の「サンプルの種別」の全て |
| 除去分（Delta） | 整音で除去した成分だけの音声（主サンプルについて1つ） |

**サンプルの種別**（目的関数 × 媒体プロファイル）

各種別を一通り聴けるように、全ての組み合わせではなく、「目的関数の軸」「媒体の軸」「2軸の合成」の3方向に沿って用意する。全部で 11 種。

| # | 目的関数 | 媒体プロファイル | 見せるもの |
|---|---|---|---|
| 1 | `comfort` | `streaming_universal` | **主サンプル**。既定の目的関数と、配信共通の出口 |
| 2 | `bass_heavy` | `streaming_universal` | 目的関数の軸: 重低音強化 |
| 3 | `vocal_forward` | `streaming_universal` | 目的関数の軸: ボーカル前面 |
| 4 | `clarity` | `streaming_universal` | 目的関数の軸: 明瞭さ（歌詞の聞き取り） |
| 5 | `low_fatigue` | `streaming_universal` | 目的関数の軸: 疲れにくさ（暫定の目的関数） |
| 6 | `comfort` | `apple_music` | 媒体の軸: −16 LUFS の出口 |
| 7 | `comfort` | `sns_hot` | 媒体の軸: SNS 専用の熱い版 |
| 8 | `comfort` | `cd` | 媒体の軸: CD（44.1 kHz / 16 bit、ディザあり） |
| 9 | `comfort` | `club` | 媒体の軸: 目的関数を変えずに出口だけクラブにした場合 |
| 10 | `club_impact` | `club` | 2軸の合成: クラブ向けの意図 × クラブの出口 |
| 11 | `bass_heavy` | `club` | 2軸の合成: 重低音強化 × クラブの出口 |

- 目的関数の強度は、全種別で既定値（0.5）にそろえる。違いが強度でなく目的関数と媒体に由来することを保つため
- 主サンプル（#1）は、納品形式 `distributor_44k16`（ディストリビューター納品の基準線）でも書き出す
- `spotify`、`youtube`、`amazon_music`、`tidal`、`sns_safe` は、ラウドネスの目標が `streaming_universal` と同じ（−14 LUFS）で、音の違いがほぼ出ない。音声は用意せず、検証結果（各プロファイルへの適合の合否）だけを表で示す
- `translation` はゲートであり、全種別に適用される。合否を表で示す
- 9 と 10 を並べることで、「出口だけ変えた場合」と「意図も変えた場合」の違いが聴ける

提示の規則:

- **レベルマッチ版を主**に置く。処理前と処理後の統合ラウドネスを揃えて聴かせる。大きい方が良く聞こえる錯覚を除くためで、この製品の思想そのものの提示でもある。揃えるときは、大きい方を下げる
- 併せて、実際の出力レベルのままの版も置く（配信や現場で実際に鳴る音量の確認用）
- 各音声に、測定値（LUFS、True Peak、主要な代理指標）と Mix Report を添える
- 処理後の音声は、本体のコマンドで再生成できる手順を記録する（手作業で作らない）。種別の一覧と再生成の手順は、サンプルの目録（manifest）として機械可読で持つ

### 15.3 サンプルの置き場と提示方法（確定。D-038、D-055）

各種別のミックス／マスタリング結果を、**リポジトリのサンプルとして用意する**（オーナー要件）。置き場を、役割で3つに分ける。

| 置き場 | 置くもの | 形式 | 役割 |
|---|---|---|---|
| **リポジトリ内 `samples/public/`** | 試聴用の音声一式（処理前、処理前のレベルマッチ版、参考フルミックス、処理後 11 種、除去分）、各種別の Mix Report、サンプルの目録 | 試聴用の音声は **MP3（320 kbps）**。Mix Report は JSON と Markdown | README から直接たどれる聴き比べの実体。ブラウザや各種アプリでそのまま再生できる形式にする |
| **GitHub の Release 添付** | 各種別のロスレスのマスター（納品形式どおり）、入力ステム一式 | マスターは FLAC または WAV。ステムは、書き出しセットをダウンロードしたままの WAV、conform 済みセットを FLAC | 原本の配布と再現性の検証用。git の履歴を太らせない |
| **Pages デモ** | `samples/public/` と同じ試聴用の音声と Mix Report | 同上 | A/B の瞬時切り替えとレベルマッチの切り替えができるプレイヤー |

- 試聴用の MP3 は**マスターではない**（§5.3 のとおり、ロッシー形式をマスターとして書き出さない）。マスターから作る試聴用の複製であり、その旨を目録と README に書く。MP3 にするのは、WAV や FLAC のままでは再生できない環境が多いためである
- 試聴用の音声は 1 本あたり約 4 MB、一式で約 60 MB になる。履歴が太らないよう、`samples/public/` の音声を更新するのは**リリースの節目だけ**とし、開発中の試作は Release 添付かローカルに置く
- レベルマッチ版をファイルとして置くのは、主サンプルの対（処理前と #1）だけとする。他の種別は、目録に「処理前と揃えるためのゲイン」を数値で持ち、Pages のプレイヤーがそれを適用する
- README の聴き比べセクションには、(1) 種別の表（目的関数、媒体、測定値、試聴ファイルと Mix Report へのリンク）、(2) Pages デモのプレイヤーへのリンク、(3) Release のロスレス音声へのリンク、を載せる
- GitHub の README が音声をどこまで直接再生できるかは、サンプルを置く時点で実物を確認して、リンクの形を最終調整する

採用しなかった方法: 静止画つきの動画に変換して README に埋め込む方法は、音声が動画用に再符号化され、A/B の切り替えもできないので使わない。

### 15.4 公開範囲と素材の保管（確定。D-038）

前提: 公式サンプルは、有料プランの契約期間中に生成され、Suno Studio のマルチトラック書き出しで得た素材であり、事前調査の範囲では商用利用が認められる。

| 項目 | 決定 |
|---|---|
| 尺 | **フル尺で公開する**（約 99 秒の短い曲であり、抜粋にすると展開のコントラストやセクション間の評価が聴けなくなる） |
| 加工後の音声 | 全種別を公開する（§15.2 の 11 種、処理前、除去分） |
| 入力ステム | **公開する**。置き場は Release 添付に限り、git の履歴には入れない。同じ入力から同じ出力を誰でも再現できることが、この製品の主張の裏付けになるため |
| 曲名 | そのまま表記する |
| 歌詞 | リポジトリには載せない（サンプルの説明に必要がない） |
| private の間の保管 | フル尺のステムはローカル（リポジトリの外）に置き、テストとサンプル生成は「サンプルの場所を外から指定する」方式にする。複数の環境で共有が必要になったら、private リポジトリの Release 添付を使う |

- **前提条件（D-062 で改訂）**: 2026-09-03 発効の Suno の規約では、商用利用に「有料プランの契約中に、Suno の提供する経路で許可されたダウンロード（書き出し）」が要る。公式サンプルの前提は、(C-1) 有料プランの契約中に生成された、(C-2) 有料プランの契約中に Suno の経路（Studio を含む）で書き出された、(C-3) 書き出しは Studio のマルチトラック書き出し、(C-4) 他の利用者の曲を元にした「Remix」ではない、(C-5) 出所（Suno で生成）を隠さない、の 5 つ。C-1〜C-4 はアカウントの事実であり、M9 の公開承認でオーナーが確認する。詳細と一次資料は `docs/PUBLICATION_AUDIT.md` §1
- サンプルの音声と入力ステムは、本体の Apache-2.0 の対象外とする（D-062）。目録、README、Release に「Suno で生成。利用条件は Suno の規約に従う。AI の学習への利用は許諾しない」旨を書く
- **公開の直前に、監査の工程（M9）で権利条件を現行の一次資料で再確認する**。確認できなかった項目は、その項目だけ公開を見送る（順に、入力ステム → フル尺 → 加工後の音声、の順で範囲を狭める）。これは監査の合否で機械的に決まる手順であり、追加の判断待ちにはしない
- 入力素材の権利状態を本ツールが判定することはない（§1.5）。上の決定は、公式サンプルという特定の素材についてのものである
- リポジトリには、サンプルの**測定値の期待範囲**（音声を含まないデータ）をテスト用に置いてよい
- `.gitignore` は音声ファイルを既定で除外し、`samples/public/` だけを例外にする

## 16. テストと検証の方針

### 16.1 層

| 層 | 内容 |
|---|---|
| 測定の適合 | ラウドネス測定を規格の適合テスト信号（EBU Tech 3341 / 3342 の考え方）で検証する。True Peak は、サンプル間ピークを持つ合成信号で検証する |
| DSP の単体 | 各プロセッサを合成信号（正弦波、スイープ、インパルス、ピンクノイズ）で検証する。周波数応答、ゲイン、時定数、レイテンシ |
| 不変条件 | S-01〜S-11 を、合成素材とランダムなパラメータで検査する（性質ベースのテスト）。整音の低域無傷はヌルテストで検査する |
| 決定性 | 同じ正本と素材から2回レンダリングし、一致を確認する |
| パイプライン | 合成のステム一式（著作権のない自作のテスト信号）で、取り込みから検証とレポートまで通す |
| スキーマとデータ | 正本、目的関数、媒体プロファイル、レジストリの JSON をスキーマで検証する。目的関数の重みの合計、未知の指標 ID、制約の緩和を検査する |
| 顔の等価性 | CLI と MCP が同じ操作で同じ正本の変更を生むことを検査する |
| GUI | 主要画面の表示と、モックバックエンドでの動作。レスポンシブの幅ごとの確認 |

### 16.2 テスト素材

- リポジトリに置くテスト素材は、合成信号と自作の短い素材に限る（生成スクリプトで作り、音声ファイルを置かない）
- 公式サンプルを使う回帰テストは、サンプルの場所を外から指定したときだけ動く任意のテストにする
- 「AI 生成音源らしい欠陥」を持つ合成テスト信号（高域の頭打ち、変調するノイズ、冒頭クリック）を用意し、整音の検出と処理を検査する

- **無加工取り込みのテスト**: Suno 書き出しセットと同じ形（「番号、空白、パート名」のファイル名、番号 0 のフルミックス、空白や日本語を含むファイル名）の合成フォルダを生成し、前処理なしで取り込めること、役割が正しく割り当てられること、取り込みの前後で素材の内容ハッシュが変わらないこと、を検査する。ステム間で尺やサンプルレートが異なる合成フォルダでは、取り込みが変換をせず、差異が報告され、変換ポリシーが記録されることを検査する
- 公式サンプルの回帰テストは、書き出しセットと conform 済みセットの両方を入力として持つ

### 16.3 再現性の基準

- 同一環境: ビット一致
- 環境をまたぐ場合（OS、CPU、FFmpeg の版）: 測定値の許容誤差内の一致。許容誤差は実装フェーズで実測して決める
- 再現性が崩れる要因（バックエンドの版の違いなど）は、レンダリング記録の比較で特定できるようにする

### 16.4 衛生とライセンスの検査

- **衛生検査**: 追跡対象のファイルに、絶対パス、ユーザー名を含むパス、メールアドレス、トークンらしい文字列がないことを検査するスクリプトを用意し、コミット前と CI で実行する
- コミットの author / committer が noreply アドレスであることを CI で検査する
- ライセンス検査は §13.4

### 16.5 聴感評価

自動指標は代理なので、人の耳による評価を検証の一部にする。

- 方式: レベルマッチ済みのブラインド A/B（提示順をランダムにする）。一度に問う観点は1つ
- 対象: 処理前と処理後、目的関数の重みの版どうし、整音の強度違い
- 評価の記録は、目的関数の重みと閾値の較正（§4.9）の入力にする
- AI 生成音源の分離と整音には公開ベンチマークがないので、自前の評価セット（公式サンプルを含む）を実装の初期に用意する
- 評価者はオーナーと、オーナーが声を掛けた協力者とする。手順はこの節の方式に従い、詳細（曲数、観点の一覧、記録の書式）は較正のマイルストーン（M10）の最初に定める（D-039）
